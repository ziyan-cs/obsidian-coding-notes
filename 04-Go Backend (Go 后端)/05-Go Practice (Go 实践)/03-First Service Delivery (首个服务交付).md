> [!abstract] 一句话结论：第一个 Go 服务的目标不是堆功能，而是完整走通 API、数据、测试、观测、部署与复盘。

> [!summary]- 复述检查：学完后再展开
>
> **回答展开**：以一个可演示 API 为切口，补齐迁移、测试、日志、指标和部署说明；每次迭代只增加一个可验证能力，并留下复盘证据。

# 推荐范围

实现一个带用户资源或短链接资源的 HTTP 服务：CRUD、参数校验、MySQL 持久化、Redis 缓存、结构化日志、优雅关闭和基础压测。

# 验收清单

- `go test` 可运行，至少覆盖一个正常与一个失败路径。
- 一个请求能在日志中通过 request ID 被定位。
- 服务被停止时不再接收新请求，并在限定时间处理已接收请求。
- README 写清启动、配置、测试和一次性能测量方法。

# 七天交付节奏

| 天数 | 可见产物 | 验收问题 |
| --- | --- | --- |
| 1 | API 契约与数据模型 | 输入、输出、错误码是否写清？ |
| 2 | 内存版 service + 单测 | 规则能否不启动 HTTP 就验证？ |
| 3 | handler + `httptest` | 协议边界是否稳定？ |
| 4 | MySQL 持久化与迁移 | 失败能否回滚或定位？ |
| 5 | Redis / 日志 / metrics | 一次请求能否被追踪？ |
| 6 | 压测与优雅关闭 | 负载和停止时有什么证据？ |
| 7 | README 与复盘 | 别人能否在干净环境复现？ |

# 交付不是“跑起来”

至少保留三类证据：一段失败路径测试、一份压测命令及结果、一条能关联日志与指标的请求记录。它们比堆叠功能更能证明工程能力，也为之后的面试项目讲解提供素材。
