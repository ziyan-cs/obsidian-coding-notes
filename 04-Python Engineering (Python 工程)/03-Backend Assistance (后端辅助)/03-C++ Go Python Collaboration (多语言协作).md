> [!abstract] 学习定位
> 按约束选语言；先用单语言完成闭环，只有边界、收益和维护责任清楚时才引入第二种语言。

| 任务 | 首选 | 选择依据 |
| --- | --- | --- |
| 高性能网络核心、现有底层设施 | C++ | 精细控制资源、内存布局与延迟 |
| 业务 HTTP/gRPC 服务 | Go | 并发模型、部署与标准库取得平衡 |
| API 回归、日志分析、数据生成 | Python | 表达快速、库丰富、适合自动化 |
| 竞赛算法与基础训练 | C++ | STL、性能与校招语境匹配 |

# 先选协作边界

语言之间的边界应比语言内部接口更粗，避免每次小函数调用都跨越进程或 FFI。

| 边界 | 适合场景 | 代价与风险 |
| --- | --- | --- |
| CLI + stdin/stdout | 构建工具、离线转换、一次性任务 | 启动进程有成本；要定义退出码和输出协议 |
| 文件/对象存储 | 批处理、报表、数据交换 | 延迟高；需要原子写、版本和清理策略 |
| HTTP/gRPC | 独立部署的在线服务 | 网络失败、超时、重试和兼容性都要设计 |
| 消息队列 | 异步任务与削峰 | 重复、延迟、乱序是正常输入 |
| FFI/共享库 | 确有证据的进程内热点 | ABI、内存所有权、崩溃隔离和发布最复杂 |

默认优先“独立进程 + 明确协议”。FFI 只有在调用频率、复制开销或延迟确实成为瓶颈，并且团队能承担 ABI 和内存安全责任时才考虑。

# 契约与失败语义

跨语言契约至少声明：

1. 输入输出的 schema、字段含义、单位、编码与版本。
2. timeout、取消与最大消息大小。
3. 哪些错误可重试，重试是否幂等。
4. 谁拥有资源、谁负责部署、升级、监控和回滚。
5. 兼容策略：新增可选字段通常比改变既有字段含义安全。

```text
Python regression tool
        |
        | HTTP contract: schema + deadline + request_id
        v
Go API service ---- database
        |
        +---- optional C++ component behind a coarse, measured boundary
```

一次调用可能出现“服务完成处理，但响应在网络中丢失”。调用方因此重试时，服务必须用幂等键或业务唯一约束避免重复副作用。不能把“客户端看到 timeout”直接等同于“服务端没有执行”。

# 三种语言在项目中的位置

一个合理练习是：Go 提供待办事项 API；Python 负责生成测试数据、执行回归和分析日志；C++ 只作为独立的连接池或序列化实验，不强行嵌入业务进程。每个部件都能单独测试、启动与替换，才算形成边界。

不要为了“技术栈丰富”把小项目拆成三种语言。下列情况通常不值得混用：

- 只有几十行可直接重写的逻辑。
- 没有性能测量，只凭“某语言更快”。
- 协议、部署、监控无人负责。
- 跨语言调试成本超过组件本身价值。

# 决策检查

> [!question]- 理解检查
> 1. 为“Go 服务 + Python 回归工具”写出契约、timeout、错误分类与版本责任。
> 2. 如果 C++ 库返回的内存由谁释放没有写入契约，会出现哪些故障？
> 3. 什么测量结果才能证明引入 FFI 比独立服务更合适？
