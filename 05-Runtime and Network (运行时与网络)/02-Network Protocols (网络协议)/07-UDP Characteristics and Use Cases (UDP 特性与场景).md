# 07-UDP Characteristics and Use Cases (UDP 特性与场景)

UDP（用户数据报协议）是传输层协议，与 TCP 并列。它的设计哲学是：**把尽可能多的控制权交给应用层，协议本身只做最少的事。**

UDP 头部只有 8 字节：

```
|0        7|8       15|16      23|24      31|
┌──────────┬──────────┬─────────────────────┐
│ Src Port │ Dst Port │                     │
├──────────┴──────────┼─────────────────────┤
│    Datagram Len     │    Checksum         │
└─────────────────────┴─────────────────────┘
```

对比 TCP 头部最少 20 字节（含序列号、确认号、窗口、标志位等），UDP 极度精简。

---

## UDP 核心特性

### 1. 无连接（Connectionless）

- 发送前不需要建立连接，直接 `sendto()` 即可发数据
- 没有握手/挥手，没有连接状态，没有连接开销
- 服务端和客户端都可以随时发送、随时停止

### 2. 不可靠传输

UDP 不提供以下任何保障：

|问题|UDP 的行为|
|---|---|
|丢包|不管，发完就不管了|
|重复包|不去重，应用层自己处理|
|乱序|不排序，到达顺序可能与发送不同|
|超时重传|没有，全靠应用层|

### 3. 面向数据报（Message-Oriented）

- 每次 `sendto()` 发送一个独立的数据报
- 每次 `recvfrom()` 接收一个完整的数据报
- **天然保留消息边界**，不存在 TCP 的粘包问题
- 但数据报大小受限：UDP 数据最大 65507 字节（65535 - IP头20 - UDP头8），超过 MTU（通常 1500 字节）会被 IP 层分片

### 4. 没有流量控制 & 拥塞控制

- 发多快就发多快，不考虑接收方处理能力
- 不感知网络拥塞，在拥塞时不会主动降速
- 这是 UDP 速度快的关键原因，也是它"不负责任"的体现

### 5. 支持广播与多播

- TCP 只能点对点（unicast）
- UDP 支持：
    - **广播（Broadcast）**：发给局域网内所有主机（255.255.255.255）
    - **多播（Multicast）**：发给一组订阅了特定多播地址的主机
    - 典型应用：局域网设备发现（mDNS、SSDP）、视频会议多方推流

## TCP vs UDP 对比

|特性|TCP|UDP|
|---|---|---|
|连接|面向连接（三次握手）|无连接|
|可靠性|可靠（重传、确认、排序）|不可靠|
|数据边界|字节流（无边界，有粘包）|数据报（有边界，无粘包）|
|头部开销|20~60 字节|8 字节|
|流量/拥塞控制|有|无|
|广播/多播|不支持|支持|
|延迟|较高（握手、重传）|低|
|吞吐量|高（大文件传输）|受限于应用层处理能力|
|适用场景|文件传输、HTTP、数据库|实时音视频、DNS、游戏|

## UDP 的适用场景

### 场景一：实时音视频（最典型）

- 视频通话（WebRTC）、直播推流、语音通话
- **为什么用 UDP**：允许丢包（丢一帧画面比等待重传更能接受），延迟比完整性更重要
- 旧数据没有意义：TCP 重传的数据到达时已经过时，还不如直接丢弃

### 场景二：DNS 查询

- 一问一答，报文小（通常 < 512 字节），不需要连接
- 若用 TCP，每次查询都要三次握手，开销大
- UDP 一个来回即可完成（若响应 > 512 字节才降级用 TCP）

### 场景三：在线游戏

- 玩家位置、操作同步对延迟极敏感
- 丢一个位置包可以由下一包补偿，不需要重传
- 游戏协议通常在 UDP 上自建轻量可靠层（只对关键数据如扣血、死亡做确认）

### 场景四：IoT / 传感器数据上报

- 设备定时上报温度、位置等数据
- 偶尔丢一条数据无所谓，不值得为此建立 TCP 连接
- MQTT over UDP（CoAP 协议）即是此类场景

### 场景五：QUIC / HTTP/3

- Google 设计的 QUIC 协议基于 UDP，替代 TCP+TLS+HTTP/2
- 在 UDP 上**自己实现**了可靠传输、流量控制、多路复用、0-RTT 连接
- 解决了 TCP 的队头阻塞问题，是现代 Web 传输的趋势

## UDP 上实现可靠传输（重点）

> 考点：为什么要在 UDP 上造可靠层？怎么造？

### 为什么不直接用 TCP？

TCP 的可靠机制是"全有或全无"的——要么所有数据都可靠，要么不用 TCP。但有些场景需要**部分可靠**：

- 只对关键消息（如开枪、扣血）重传，不对位置同步重传
- 需要多路复用但不想要 TCP 的队头阻塞
- 需要在 UDP 上自定义重传策略（如只重传最新状态，而不是历史数据）

### 实现要素

在 UDP 上构建可靠层，需要应用层自己实现：

```
┌─────────────────────────────────────────────────────────┐
│       Application-Layer Reliable Protocol               |
│                                                         │
│  1. Sequence Number       → Detect out-of-order & du    │
│  2. ACK Confirmation      → Know whether peer received  │
│  3. Timeout Retransmission → Resend after packet loss   │
│  4. Sliding Window        → Control transmission rate   │
│  5. Heartbeat Detection   → Check peer liveness         │
└────────────────────────┬────────────────────────────────┘
                         ↓ Based on
┌─────────────────────────────────────────────────────────┐
│                       UDP                               │
└─────────────────────────────────────────────────────────┘
```

### 典型实现：KCP 协议

KCP 是一个开源的、基于 UDP 的可靠传输协议（ARQ），被广泛用于游戏和实时通信：

- 以**10%~20% 带宽换取更低延迟**（比 TCP 平均延迟降低 30%~40%）
- 不管理连接，不负责底层传输，只负责数据的可靠有序送达
- 支持多种工作模式：普通模式（类 TCP）、快速模式（牺牲带宽换延迟）

### 对比：纯 UDP vs 可靠 UDP vs TCP

| |纯 UDP|可靠 UDP（KCP 等）|TCP|
|---|---|---|---|
|延迟|最低|低|较高|
|可靠性|无|可定制|完全可靠|
|灵活性|最高|高|低|
|实现复杂度|极低|高|无需关心|
|典型场景|DNS、视频流|游戏、QUIC|HTTP、文件传输|

## UDP 编程接口

```c
// 服务端
int fd = socket(AF_INET, SOCK_DGRAM, 0);   // SOCK_DGRAM = UDP
bind(fd, ...);

// 接收（recvfrom 同时获取发送方地址）
struct sockaddr_in client_addr;
socklen_t addrlen = sizeof(client_addr);
char buf[1024];
recvfrom(fd, buf, sizeof(buf), 0,
         (struct sockaddr*)&client_addr, &addrlen);

// 发送（sendto 每次指定目标地址）
sendto(fd, buf, len, 0,
       (struct sockaddr*)&client_addr, addrlen);
```

- UDP 服务端只需要一个 fd，不需要 `listen()` 和 `accept()`
- `recvfrom()` 和 `sendto()` 每次都携带地址，因为 UDP 无连接状态

## 常见误区

|误区|正解|
|---|---|
|"UDP 完全不可靠，生产不能用"|WebRTC、QUIC、KCP 都在生产大规模使用|
|"UDP 没有拥塞控制，会导致网络崩溃"|大流量 UDP 确实可能挤占 TCP，需要应用层自己限速|
|"UDP 数据报不会分片"|超过 MTU 仍会被 IP 层分片，分片丢失会导致整个数据报丢失，建议应用层控制包大小 < 1472 字节|
|"UDP 没有粘包问题就不用处理边界"|消息边界保留，但仍需处理大包分片、乱序等问题|
