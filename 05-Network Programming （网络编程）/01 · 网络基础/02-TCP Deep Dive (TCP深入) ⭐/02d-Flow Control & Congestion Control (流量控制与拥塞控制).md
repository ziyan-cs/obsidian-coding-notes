

## 流量控制
#network #tcp #flow-control #receiver-window #transport-layer

## ⚡ TL;DR（快速决策）

- 流量控制的核心是：**避免发送方发得过快，超过接收方处理能力**
- 它关心的是接收方是否来得及收，而不是网络是否拥堵
- TCP 主要通过接收窗口机制实现流量控制

## 🧩 Core Idea（核心本质）

- 即使网络通畅，接收方缓冲区也可能来不及处理大量数据
- 一句话理解：
    - **流量控制是发送速率对接收能力的匹配机制。**

## 🏗️ 关键概念

1. 接收窗口（rwnd）

- 接收方通告自己当前还能接收多少数据

1. 发送速率限制

- 发送方根据窗口大小调整未确认数据量

1. 零窗口

- 接收方暂时无可用缓冲区时，可通告 0
- 发送方需等待窗口恢复

## 🔧 Usage Patterns（可复用理解框架）

1. 用“接收方能力限制发送方”理解流量控制
2. 区分流量控制与拥塞控制

- 流量控制：防止压垮接收方
- 拥塞控制：防止压垮网络

## ⚠️ Pitfalls（高频错误）

- 把流量控制和拥塞控制混为一谈
- 只记窗口概念，不理解窗口是在表达接收能力
- 忽略应用处理速度和接收缓冲之间的关系

## 🚀 Performance / Tips（理解深化）

- 流量控制保证的是通信双方速率协调，不是全网性能最优
- 理解接收窗口后，再看 TCP 发送窗口和拥塞窗口会更清晰

## 🧪 Common Scenarios（常见使用场景）

- 理解大文件传输中的发送节奏
- 理解慢接收端为何会限制 TCP 吞吐
- 为 TCP 机制整体学习打基础

## 🧾 Minimal Template（最小理解模板）

```
接收方通告可接收窗口 -> 发送方按窗口发送 -> 避免压垮接收方
```

## 📌 One-liner Summary（一句话总结）

- **流量控制的核心，是根据接收方处理能力限制发送速率，避免接收端缓冲失控。**
## 拥塞控制
#network #tcp #congestion-control #cwnd #network-performance

## ⚡ TL;DR（快速决策）

- 拥塞控制的核心是：**避免发送方把网络链路和中间节点压垮**
- 它关心的是整个网络承载能力，而不是单个接收方缓冲区
- TCP 常见机制包括：
    - 慢启动
    - 拥塞避免
    - 快重传
    - 快恢复

## 🧩 Core Idea（核心本质）

- 网络带宽和路由器缓冲都是有限资源
- 若发送端盲目提高速率，可能造成排队、丢包和吞吐下降
- 一句话理解：
    - **拥塞控制是发送速率对网络承载能力的动态匹配。**

## 🏗️ 关键概念

1. 拥塞窗口（cwnd）

- 反映发送方当前认为网络可承受的发送量

1. 慢启动

- 初期快速探测可用带宽，但不是“慢”地增长

1. 拥塞避免

- 在接近网络极限时更平滑增长

1. 丢包信号

- TCP 常把丢包视作拥塞的重要信号之一

## 🔧 Usage Patterns（可复用理解框架）

1. 区分流控与拥塞控制

- 流控看接收端
- 拥塞控制看网络路径

1. 用“探测 - 退让 - 再探测”理解 TCP 速率调节

## ⚠️ Pitfalls（高频错误）

- 把丢包只理解成链路质量差，不考虑拥塞含义
- 把慢启动误以为一直低速
- 不区分拥塞窗口和接收窗口

## 🚀 Performance / Tips（理解深化）

- TCP 吞吐不仅由带宽决定，也受 RTT、丢包、拥塞控制策略影响
- 理解拥塞控制后，更容易理解高并发网络服务中的性能波动

## 🧪 Common Scenarios（常见使用场景）

- 理解网络高峰期吞吐下降
- 分析长距离传输和高丢包链路表现
- 为 TCP 优化和网络性能分析打基础

## 🧾 Minimal Template（最小理解模板）

```
探测可用带宽 -> 接近极限时放缓 -> 出现拥塞信号后退让 -> 再继续探测
```

## 📌 One-liner Summary（一句话总结）

- **拥塞控制的核心，是动态调整发送速率以适应网络路径的真实承载能力。**
