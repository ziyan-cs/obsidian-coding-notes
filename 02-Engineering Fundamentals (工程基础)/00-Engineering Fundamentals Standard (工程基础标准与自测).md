> [!abstract] 完成标准
> 工程基础不是工具命令合集，而是把一次修改变成可复现、可审查、可验证、可交付的软件变更。完成本模块后，应能从源码、依赖、构建、测试到性能证据独立闭环。

## Git 与交付

- [ ] 能解释工作区、暂存区、本地提交与远端引用，判断一个操作会改变哪一层状态。
- [ ] 能用小提交、清晰消息和可审查 diff 表达修改意图，并安全处理冲突、回退和历史整理。
- [ ] 能设计分支保护、代码评审和 CI 检查，使错误尽量在合并前暴露。
- [ ] 能区分 revert、restore、reset 与 rebase 的影响范围，不用破坏历史的命令碰运气。

## 构建与依赖

- [ ] 能说明预处理、编译、链接、装载以及静态库、动态库、ABI 之间的关系。
- [ ] 能从干净环境复现构建，固定工具链与依赖，并追踪产物由哪些输入生成。
- [ ] 能维护 CMake target、include、link 与 install 边界，避免全局配置和传递依赖失控。
- [ ] 能识别依赖冲突、符号缺失、ODR、运行库不一致和供应链风险，并保留诊断证据。

## 验证与诊断

- [ ] 能从风险和不变量反推单元、组件、契约、集成、端到端、性质与故障测试，而不是只追求覆盖率数字。
- [ ] 能保存现场、建立最小复现，用调试器、core dump、系统调用和对照实验找到首次错误状态。
- [ ] 能选择 sanitizer、Valgrind 与静态分析检查内存、未定义行为和数据竞争，并解释工具盲区。
- [ ] 能建立性能基线，区分延迟、吞吐、资源、并发和尾延迟，用 profile 验证瓶颈与优化收益。
- [ ] 能设计低基数指标、结构化日志和分布式追踪，以 SLI/SLO 和用户影响驱动告警。
- [ ] 能从威胁场景设计安全检测，验证规则并保全带来源、时间与哈希的事件证据。
- [ ] 能把测试、安全、制品完整性与灰度观测组织成发布门禁，并预先定义暂停和回滚条件。

## 自动化与可审查证据

- [ ] 能让格式化、静态检查、测试、构建和制品生成通过脚本或 CI 一键运行。
- [ ] 能记录操作系统、编译器、依赖版本、输入数据、命令与结果，使结论可复核。
- [ ] 能让失败输出具有可行动性：指出阶段、原因、上下文与下一步，而不是只返回非零状态。
- [ ] 能把一次线上或开发故障沉淀为测试、检查规则、运行手册或设计约束。

## 综合自测

1. 一个修改在本机通过、CI 链接失败，你会如何区分环境、依赖、ABI 和构建图问题？
2. 某提交引入故障但后面已有多人提交，为什么通常优先 revert，而不是改写共享历史？
3. benchmark 快了 30%，需要记录哪些条件才能证明它不是噪声或换取了不可接受的代价？
4. 测试全部通过但线上仍失败，测试金字塔中可能缺少哪一层，如何补充最小证据？
5. 一个告警只有「CPU 高」，为什么不足以指导行动？你会怎样把它连接到用户影响、trace 与 profile？
6. 一条安全检测规则如何证明既能识别目标行为，又不会在正常高峰制造告警风暴？
