> [!abstract] 学习目标
> 知道“能在本机编译”和“他人能重建同一制品”差在哪里；能够记录依赖解析、工具链与环境输入，并区分可复现、可验证来源和供应链可信度。

# 可复现有不同强度

| 目标 | 判定 |
|---|---|
| 功能可重建 | 同源代码能构建并通过相同功能测试 |
| 依赖解析可重现 | 同一组直接/传递依赖与来源 |
| 字节可复现 | 独立构建的产物字节完全相同，摘要一致 |
| 来源可验证 | 能核对制品来自预期源码、构建环境和流程 |

这四项不能互相替代。编译成功不证明输出相同；两个相同 hash 不证明上游无恶意代码；有 attestation 但消费端不验证也没有建立信任。

# 完整构建输入

```text
源代码 + 子模块/生成源 + 依赖图 + 工具链/标准库
       + 构建脚本/选项 + OS/基础镜像 + 环境变量
       + locale/时区/时间戳/随机种子 + 外部服务
       → 制品
```

常见遗漏：编译器 patch 版本、系统头文件、下载镜像内容、代码生成工具、`__DATE__`、文件遍历顺序、嵌入绝对构建路径、未固定的远端 tag、缓存中的旧产物。

锁文件只是依赖解析输入的一部分，且其能力随包管理器而异；不要假设每种 C++ 包管理器都有 npm 式完整锁文件。

# 依赖图与 SBOM

```text
application
├── library-a ── common-x
└── library-b ── common-x
```

升级 library-a 可能改变 common-x 的选择，即使 application 的直接依赖没变。依赖图应记录版本、来源、构建配置、许可证及可达性。SBOM（software bill of materials）帮助盘点制品包含的组件，但它不是漏洞已经存在或可被利用的证明，还需分析调用路径和部署暴露面。

# 复现的操作流程

1. 从明确 commit/tag 检出源码，并记录其 commit ID；
2. 使用固定的编译器、构建工具和基础镜像/环境（镜像优先记录 digest）；
3. 在空构建目录安装由受控配置解析的依赖，记录完整依赖图；
4. 执行同一 configure/build/test 命令并保存日志；
5. 对产物计算摘要，若不同使用 `diffoscope` 等工具定位差异；
6. 修正时间戳、路径、随机数等非确定输入，再做两次独立构建。

关闭缓存可以发现隐式本机依赖；并不要求生产每次构建都关闭缓存。缓存键须覆盖影响输出的输入；缓存是加速层，不是可信来源。

# 供应链与权限

风险可能来自依赖混淆、名称仿冒、发布者账号被盗、恶意安装脚本、受污染缓存、CI 凭据泄漏和可变制品标签。控制手段包括：

- 最小权限的 CI 身份、隔离不可信 PR；
- 审查依赖来源、许可证与维护状态；
- 使用固定修订/摘要并管理更新窗口；
- 记录 SBOM、制品摘要与构建 provenance；
- 对重要制品签名/出具 attestation，并在使用端验证；
- 漏洞告警结合可达性和实际部署评估，不以扫描分数代替判断。

绝对可复现不意味着绝对安全：若受控源码或编译器本身恶意，完全一致的输出仍会有问题。

# 升级与发布决策

依赖升级不只是把版本字符串改大。至少检查：

```text
变更日志/迁移指南 → API/ABI 差异 → 许可证/安全公告
→ 锁定解析结果 → 清洁构建与测试 → 性能/资源影响
→ 分阶段发布 → 运行期观察与回滚
```

回滚应用不一定能回滚数据迁移；切换静态/动态库也可能改变运行期查找路径。发布记录应关联源码提交、依赖图、制品摘要和部署环境。

# 检查理解

1. 为什么仅固定依赖版本不足以保证制品 hash 一样？
2. SBOM、hash、签名和 attestation 分别能证明什么，不能证明什么？
3. 缓存命中为何不能替代一次空缓存构建？
4. 发现依赖漏洞后，为什么不能只看包名和 CVSS 分数决策？

> [!summary] 本篇结论
> 可复现构建是对**全部影响输出的输入**施加控制、记录和比较；供应链安全还要验证来源与权限。两者相互支持，但不能互相冒充。
