> [!abstract] 完成标准
> 求职模块把技术能力压缩成准确、可追问、可举证的表达。目标不是背统一答案，而是在有限时间内呈现问题、机制、取舍与证据。

# 技术表达

- [ ] 回答概念题时能先给定义与结论，再讲机制、边界和工程例子。
- [ ] 能在白板或纸上画出内存、线程、网络、事务和分布式流程，并主动标出异常路径。
- [ ] 不使用“绝对不会”“一定更快”等无条件结论；性能与版本问题会说明前提。
- [ ] 不会的问题能明确已知边界、提出验证方法，不用模糊术语掩饰。

# 项目追问

- [ ] 能区分团队结果和个人贡献，用代码、指标、测试或故障记录证明工作。
- [ ] 能解释关键难点为什么难、候选方案、选择依据、实施结果和复盘。
- [ ] 能回答容量、并发、数据一致性、故障恢复、安全和可观测性追问。
- [ ] 能从一次请求出发串联语言运行时、网络、存储和部署链路。

# 系统设计

- [ ] 能先澄清功能需求、规模和 SLO，再进行 API、数据模型与架构设计。
- [ ] 能识别状态、热点、单点、瓶颈和故障域，并提出逐步演进方案。
- [ ] 能讨论一致性、可用性、成本、复杂度和团队能力之间的取舍。
- [ ] 能说明监控、压测、灰度、回滚和灾难恢复，而不只画正常路径。

# 求职执行

- [ ] 简历每项技术表述都有可复核证据，能经受连续追问。
- [ ] 建立按主题记录的错题与薄弱点，并依据表现调整复习而非机械刷题。
- [ ] 能完成限时编码、代码解释、测试与复杂度分析。
- [ ] 面试后记录问题、答题缺口和下一次具体改进动作。

# 综合自测

1. 随机抽一篇主线笔记，你能否在 30 秒和 3 分钟两种时长内分别讲清？
2. 项目指标来自哪里，测试条件是什么，结果能否由他人复现？
3. 当面试官反驳你的方案时，你能否先确认约束，再比较方案而不是防御性争辩？
4. 最近一次答错的问题，根因是知识缺口、表达混乱还是缺少实践证据？
