# 写作规则

- 一篇只回答一个核心问题；超过两个独立问题就拆分或改为导航页。
- 首次出现写“中文（English term）”，后续优先使用英文术语。
- 代码标注语言与版本；若未执行，明确写“未运行”。
- “高性能”“线程安全”“推荐”等结论必须写条件与代价。
- 工具/API/版本类信息记录一手来源与 `verified` 日期。
- 一级标题一篇只能有一个；正文从二级标题开始。使用 `abstract`、`warning`、`tip` callout 时，每段只服务一个阅读目的。

# 旧笔记渐进改造顺序

1. 先保留正确知识，删掉重复、无来源数字和错误结论。
2. 重写一句话结论、问题、心智模型、最小例子与边界。
3. 给最关键的 5–15 行代码补输入约束、失败场景或解释。
4. 需要时再加跨语言对照；最后按新知识依赖重建关联链接。

# 从零建立模型

本页主题是 **03-Note Standard (笔记规范)**。先明确本页解决的具体问题、输入输出和适用边界；再用一个最小例子观察机制如何改变状态或结果。术语必须能被复述为因果关系，而不是孤立定义。

# 最小实践

写一个最小示例、反例或测试，验证本页一条关键结论；记录预期和实际结果。

# 工程检查点

将结论与其前提、失败模式和替代方案一起记忆，不把单次观察当成通用规律。



# 渐进练习

1. **第一步 · 理解**：读：不看正文复述问题、关键状态和适用边界。
2. **第二步 · 实现**：写：做一个最小样例或反例，记录预期与实际结果。
3. **第三步 · 验证**：验：改变一个关键条件，解释结果为何改变，以及何时应换方案。

# 常见误区

- 只背结论而不说明它成立的前提、失败模式和替代方案。
- 不通过最小代码、测试、测量或项目现象验证，就把理解误当成掌握。

# 学习闭环

## 从零复述

- 不看正文，用“问题 → 机制 → 边界”三句话讲清 **03-Note Standard (笔记规范)**。

## 最小验证

- 写一个最小代码、命令、测试或项目观察，亲自验证本页的一条关键结论。

## 自测

1. 它解决的工程问题是什么？
2. 核心机制在哪个环节生效？
3. 什么时候应当换用另一种方案？
