> [!abstract] 学习定位：错误不是“不会”，而是下一次可被提前识别的触发条件。

# 30 秒回答

**核心结论**：错误不是“不会”，而是下一次可被提前识别的触发条件。


# 使用方式

只记录会重复、代价高或暴露认知缺口的错误。题目答案、报错全文不必搬运；记录**错误模式**。

# 模板

```md
## YYYY-MM-DD — 简短标题
- 分类：算法 | C++ | Go | Python | Linux | 数据库 | 项目设计 | 工具
- 触发场景：
- 我当时的错误判断：
- 根因：知识缺口 | 边界遗漏 | 调试方法错误 | 操作疏忽
- 正确模型 / 修正：
- 最小复现或反例：
- 下次触发器：看到 ___ 时先检查 ___。
- 关联：[[笔记名]]
- 复习日：YYYY-MM-DD
```

# 高频触发器

| 看到什么 | 先检查什么 |
| --- | --- |
| 指针、view、引用或回调 | 所有者是谁？对象何时销毁？ |
| 多线程共享状态 | 是否有数据竞争？锁顺序和退出路径完整吗？ |
| Go goroutine | 是否有退出条件？`context` 是否传播？channel 是否可能阻塞？ |
| Python 容器/函数默认值 | 是否意外共享可变对象？环境与依赖是否隔离？ |
| 数据库更新/消息消费 | 是否幂等？失败重试会怎样？ |
| 性能“优化” | 先测量了吗？指标是延迟、吞吐、内存还是 CPU？ |

# 复盘频率

- 每周：读本周新增错误，提取最多 3 个下周规则。
- 每月：合并重复条目，把稳定规则写回对应主题笔记。



# 从零建立模型

本页主题是 **05-Mistake Log (错误记录)**。先明确本页解决的具体问题、输入输出和适用边界；再用一个最小例子观察机制如何改变状态或结果。术语必须能被复述为因果关系，而不是孤立定义。

# 最小实践

写一个最小示例、反例或测试，验证本页一条关键结论；记录预期和实际结果。

# 工程检查点

将结论与其前提、失败模式和替代方案一起记忆，不把单次观察当成通用规律。



# 渐进练习

1. **第一步 · 理解**：读：不看正文复述问题、关键状态和适用边界。
2. **第二步 · 实现**：写：做一个最小样例或反例，记录预期与实际结果。
3. **第三步 · 验证**：验：改变一个关键条件，解释结果为何改变，以及何时应换方案。

# 常见误区

- 只背结论而不说明它成立的前提、失败模式和替代方案。
- 不通过最小代码、测试、测量或项目现象验证，就把理解误当成掌握。

# 学习闭环

## 从零复述

- 不看正文，用“问题 → 机制 → 边界”三句话讲清 **05-Mistake Log (错误记录)**。

## 最小验证

- 写一个最小代码、命令、测试或项目观察，亲自验证本页的一条关键结论。

## 自测

1. 它解决的工程问题是什么？
2. 核心机制在哪个环节生效？
3. 什么时候应当换用另一种方案？
