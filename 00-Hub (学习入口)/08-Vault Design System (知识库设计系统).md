> [!abstract] 设计目标
> 让每篇笔记像同一套工程教材中的一章：先建立问题与心智模型，再解释机制、边界、失败方式和验证方法；目录负责领域定位，标题负责文章内部结构。

# 固定架构

```text
00-Hub                                  学习入口、路线、复习与维护规则
01-Foundations                          计算机核心、算法、数学与基础实践
02-Engineering Fundamentals             Git、构建、依赖、验证与诊断
03-C++ Backend                          C++ 语言、资源、STL、并发与工程实践
04-Python Engineering                   Python 基础、质量、自动化与后端辅助
05-Go Backend                           Go 语言、运行时、服务与数据集成
06-Systems and Networking               Linux、网络协议与服务器网络编程
07-Data Systems and Distributed Computing  数据库、缓存、消息与分布式基础
08-Cloud Native and Reliability         容器、Kubernetes、平台工程与 SRE
09-Security Engineering                 应用、身份、供应链、隔离、检测与响应
10-AI Systems Engineering               AI 基础、LLM 应用、Agent 与推理基础设施
11-Projects                             项目方法与可运行后端项目
12-Career                               面试表达、系统设计、求职与决策记录
assets                                  图片与附件，不存放知识正文
```

- 顶层编号表达知识依赖，不代表必须串行学完。项目从早期开始，随主线知识逐次升级。
- 目录固定为“顶层领域 / 二级主题 / 笔记”，不在二级主题中继续创建导航文件或第四层目录。
- 每个一级学习模块只保留一篇 `00-... Standard`，用于开始前校准目标、学完后验收。
- 二级主题原则上至少三篇实质笔记；主题不足以支撑三篇时，优先并入相邻主题而不是制造碎片。

# 页面结构

文件名已经承担文章标题，正文不重复同名一级标题。普通教学笔记通常使用 2～7 个一级模块，每个模块回答一个完整问题。

```md
> [!abstract] 学习定位
> 给出可复述的中心判断。

# 问题与心智模型
# 核心机制
## 必要的内部步骤
# 工程边界与失败路径
# 实验或实践
> [!question]- 理解检查
```

- 一级标题构成文章骨架；二级标题只拆解一级主题；三级标题只用于确有并列步骤的复杂部分。
- 不为两三句话单独创建标题，不机械添加“学习闭环”“总结”“关联学习”等弱信息章节。
- 核心摘要直接展示主题、机制与边界；综合自测集中在模块 `00` 标准页。
- 表格只用于稳定的并列比较；流程优先用短列表或 ASCII 图，中文字符无法可靠等宽时不强求画框对齐。

# 内容质量门槛

一篇教学笔记至少要能支持初学、复查和工程迁移：

1. **问题**：技术为何存在，解决什么约束。
2. **机制**：数据、控制、资源或状态怎样变化。
3. **边界**：前提、复杂度、版本差异与不适用场景。
4. **失败路径**：常见错误怎样发生，现象是什么。
5. **验证**：最小代码、测试、命令、抓包、指标或实验如何证明结论。

概念简单时可以短，但不能只放定义、面试话术或无法运行的代码片段。性能数字必须携带环境、负载、样本与测量方法；版本行为以官方文档和目标环境验证为准。

# 来源与链接

- 规范、API 和版本行为优先引用官方文档、标准、RFC、论文与权威教材。
- 内部链接只表达真正的前置、后续、对照或项目应用关系，通常保留 2～5 条即可。
- 稳定原理与易变实现分开书写；易变项记录验证日期与适用版本。
- 合并旧笔记时重建文章逻辑，不保留失去上下文的分隔线、跳转句和拼接标题。

# 验收问题

打开任一页面，应能在十秒内看出它解决什么问题；读完后应能回答“为什么这样设计、什么时候失效、怎样验证”。模块学习是否完成，以对应标准页和项目证据判断，不以阅读数量判断。
