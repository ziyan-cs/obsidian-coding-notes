# 08-Vault Design System (知识库设计系统)

> **目标**：让每一篇笔记看起来像同一套教材的一个章节，而不是不同阶段收集的网页摘录。

## 目标架构

```text
00-Hub                         学习入口、路线、复习、术语、错误与规范
01-Foundations                 CS Core 与 Algorithms
02-C++ Backend                 C++ 语言、STL、并发、性能与工程实践
03-Backend Systems             Linux、Network、Database、Redis、MQ、Distributed
04-Engineering Tools           Git、CMake、调试、测试、性能工具
05-Go Backend                  Go 语言、并发、HTTP、服务工程
06-Python Engineering          Python 自动化、测试、数据与脚本工程
07-Projects                    可运行项目、设计、测试、压测与复盘
08-Career                      面试表达、系统设计、简历与学习策略
assets                         图片与附件，不放知识正文
```

- 顶层顺序表达学习依赖：基础与 C++ 打底，系统知识支撑后端，Go/Python 作为主动发展的工程语言，项目与校招用于能力证明。
- 目录最多三级：`顶层领域 / 二级主题 / 笔记`；只有同一主题下存在多个互相依赖的小节时才使用第三级。
- 每个顶层目录只有一个 MOC（Map of Content）作为入口；MOC 只导航，不重复正文。

## 页面语言与视觉规范

### 标题

```md
# English Topic — 中文主题
```

- 英文保留规范术语、API、协议名和代码实体；中文承担解释。
- 一级标题一篇只能有一个；正文从 `##` 开始。
- 不使用“核心”“总结”“杂项”作为孤立标题，必须说明主题，例如 `## 解决的问题`、`## 关键边界`。

### 开场与正文

```md
> [!abstract] 一句话结论：……

## 解决的问题
## 心智模型
## 最小例子
## 边界与误区
## 30 秒回答
## 自测
## 关联
```

- 不要求每篇机械填满所有段落；概念简单时宁可短而完整。
- 每段先给结论，再解释原因；表格只用于比较，代码只保留能运行或能说明关键机制的最小片段。
- 使用 `warning` 写前提、风险和版本差异，使用 `tip` 写实践建议，避免连续堆叠 callout。

### 内容正确性

- 性能、内核参数、框架版本、默认行为必须写条件、来源或 `NEEDS_VERIFY`；不使用无来源固定倍数。
- 原理笔记必须给反例或“不适用场景”；代码模板必须说明输入约束和失败路径。
- 旧笔记允许重写、合并或拆分；保留的是正确知识与可复用代码，不是原来的段落结构。

## 重写优先级

1. **高频主线**：C++ 所有权/并发，Linux I/O，网络服务，MySQL/Redis，Go HTTP。
2. **实践闭环**：项目、测试、压测、调试和错误复盘。
3. **算法表达**：识别信号、错误模式、复杂度与模板边界。
4. **低频理论**：按真实项目或面试需求重写，不为数量扩充。

## 迁移原则

1. 先建立新目录与目录映射，再移动文件；迁移后立即校验所有 Markdown 与 wikilink。
2. 文件名使用 `序号-English Topic (中文主题)`；星标只保留真正的主线必背页。
3. 合并重复主题时，把旧页面改为明确的索引或删除；不保留内容空壳。
4. 每完成一个顶层域，检查 Obsidian 大纲、链接、MOC 和视觉层级，再进入下一域。

## 完成标准

打开任一页面时，应在 10 秒内看出它解决什么问题、处于哪条学习主线、需要记住什么、以及下一步读哪里。
