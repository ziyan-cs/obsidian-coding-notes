> [!abstract] 本篇要点
> > 简历不是知识清单，而是可核验的能力索引；每条项目描述都应指向问题、行动、约束、结果和证据。
>
> 用“在什么约束下解决什么问题—我做了哪项关键决策—结果如何验证”描述经历。数字必须能解释测量环境和基线；仓库、测试、文档、压测与故障复盘共同构成证据链，无法追问的名词不要写进简历。

# 项目条目的结构

```text
背景与约束 -> 个人职责 -> 技术决策 -> 可验证结果 -> 边界与反思
```

弱描述：“使用 Redis、MySQL、Docker 完成后端项目。”

强描述关注为什么使用、承担何种职责、失败时如何处理，以及数据来自什么实验。结果不一定是夸张的性能提升，也可以是覆盖了关键失败场景、缩短复现步骤或明确容量上限。

# 证据分级

- 一级：可运行仓库、自动化测试、部署说明。
- 二级：压测脚本、环境参数、原始数据、火焰图或抓包。
- 三级：架构图、决策记录、故障复盘。
- 口头主张：没有材料支撑，只能视为待验证。

# 作品集最小入口

每个核心项目应让面试官在几分钟内找到：

1. 项目解决的问题和运行截图或请求示例。
2. 一键启动与最小演示命令。
3. 架构、数据模型和关键权衡。
4. 测试、压测和已知限制。
5. 你个人完成的范围。

# 防止数字失真

写 QPS、延迟或提升比例时，同时保留机器配置、并发模型、数据规模、请求分布、预热方式和错误率。不同条件下的数字不能直接比较。

# 发布前检查

- [ ] 每个技术名词都能解释机制、选择理由和替代方案。
- [ ] 每个数字都有命令、环境和原始结果。
- [ ] 仓库已清理密钥、个人路径和无关生成物。
- [ ] 项目描述能明确区分个人工作与团队成果。

> [!question]- 自测：先回答再展开
> 1. 面试官沿哪条链接能验证你最重要的一项能力？
> 2. 哪条简历表述最容易被连续追问击穿？
> 3. 如果去掉所有框架名，你还能否讲清工程价值？

# 考察题目

## 1. 动手题

将一条“提升性能”的简历描述链接到原始压测、代码改动和复现 README，请他人验证。

> [!note]- 验收要点
> 数字有基线、环境、样本和边界；作品入口无隐藏依赖。

## 2. 机制追问

简历写“性能提升 50%”时，怎样让表述可核验？

> [!note]- 参考答案
> 附上原始基线、测试环境、负载模型、指标定义和改动范围，说明个人贡献与适用边界；作品入口应可复现演示。
