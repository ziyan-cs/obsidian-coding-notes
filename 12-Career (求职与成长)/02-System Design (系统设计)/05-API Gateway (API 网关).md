> [!abstract] 本篇要点
> API 网关负责入口路由、统一认证、流量治理和代理观测；下游服务仍负责具体资源授权。过滤器、重试和配置发布都要受明确的预算与失败语义约束。

# 需求与责任边界

| 边界 | 网关负责 | 下游负责 |
| --- | --- | --- |
| 身份 | 验证凭据并传递可验证身份 | 按资源、动作和租户授权 |
| 流量 | 请求大小、并发与速率限制 | 业务容量和内部排队上限 |
| 失败 | 总超时、连接错误、有限重试 | 幂等、事务与业务错误 |
| 观测 | 请求 ID、入口延迟、路由与状态 | 业务结果与依赖证据 |

若需要对外公开 API，先确定路由、版本、TLS 终止、鉴权来源和错误契约。不要把所有业务规则塞进网关，也不要把网关认证视作下游授权的替代。

# 请求路径

```mermaid
flowchart LR
    A[客户端] --> B[入口与 TLS]
    B --> C[路由与请求限制]
    C --> D[认证与入口限流]
    D --> E[代理与总超时]
    E --> F[下游资源授权]
    F --> G[业务处理]
    G --> H[响应、日志与指标]
```

过滤器顺序应在契约中固定，例如先限制请求大小，再认证、限流与代理；错误返回要说明哪个边界拒绝了请求。身份传递须防止客户端伪造内部头，网关与下游之间使用受信任的连接和明确的凭据机制。

# 重试与配置

只对允许重试的请求和瞬态错误尝试重试；总 deadline、次数、退避和下游负载必须有上限。非幂等写入若没有业务幂等键，网关不能自行重放。熔断用于限制持续故障的流量，不能掩盖真实错误或无限排队。

路由与策略配置应版本化、可灰度、可回滚。代理节点以完整配置快照切换；发布失败时保留上一个有效版本，不让不同过滤器读到混合配置。

# 验证与性能

用目标负载测入口和下游各自的延迟、错误率、连接数与队列长度，再决定本地或共享限流、代理线程数和实例规模。测试认证失败、限流、下游超时、响应丢失、重复重试、配置回滚与身份头伪造；性能数字必须附机器、请求大小和负载条件。

# 考察题目

## 1. 动手题

为网关写路由、认证、限流、超时和下游授权边界；注入一个下游失败。

> [!note]- 验收要点
> 网关不代替业务授权，失败隔离与重试有预算，身份传递可验证。

## 2. 机制追问

网关鉴权通过后，下游服务还需做授权吗？

> [!note]- 参考答案
> 需要。网关适合统一认证、限流和路由，下游仍需按具体资源与业务动作授权；信任边界和身份传递要可验证。
