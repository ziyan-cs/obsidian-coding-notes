> [!summary] 核心摘要
>
> TCP 可靠性由序列号、确认、重传与有序交付共同实现；流量控制保护接收端，拥塞控制保护网络。发送窗口同时受接收窗口和拥塞窗口约束，调优必须区分丢包、接收端变慢与网络拥塞。
>

> [!note] 本节重点：两者的区别、滑动窗口、拥塞控制四个阶段

# 核心区别

| |流量控制|拥塞控制|
|---|---|---|
|解决的问题|发送方太快，**接收方**处理不过来|发送方太快，**网络**承载不了|
|依据|接收方通告的窗口大小（rwnd）|发送方自己估算的拥塞窗口（cwnd）|
|控制方|由接收方控制|由发送方自主控制|
|机制|接收窗口通告|拥塞窗口与算法状态；下文以 Reno 教学模型说明|

> **可在途上限**受 `min(rwnd, cwnd)` 约束；还能新发多少，需再扣除已发送未确认数据，并受应用是否有数据可发影响。它不是“实际发送量”的等式。

# 流量控制：滑动窗口

接收方在每个 ACK 中携带 **rwnd（接收窗口）** 字段，告知发送方自己还能接收多少字节。

```
接收方缓冲区：[ 已消费 | 已收到待消费 | 可接收空间(rwnd) | ... ]

发送方维护一个窗口，窗口内的数据可以连续发送无需等待 ACK：

发送缓冲区：
| 已发已确认 | 已发未确认 | 可发未发 | 不可发 |
             ↑           ↑
           SND.UNA   SND.NXT
           |←── 窗口大小 ──→|
```

## 零窗口与窗口探测

- 接收方缓冲区满时，通告 **rwnd = 0**，发送方必须停止发送
- 发送方按持续定时器发送**窗口探测**，等待接收方更新窗口；其具体报文形式与时机由 TCP 实现决定
- 若一直不更新，可能触发死锁 → 依赖**持续定时器**打破

# 拥塞控制：先学 Reno 教学模型

慢启动、拥塞避免、快重传、快恢复是理解经典 TCP Reno 的框架，不代表每个现代 Linux 连接都严格按下面的四格流程运行。SACK、RACK-TLP、CUBIC、BBR 与 ECN 会改变丢包检测和增减窗口策略；抓包时要核对主机当前算法与内核配置。

## 关键变量

- **cwnd**（拥塞窗口）：发送方维护，根据网络状况动态调整
- **ssthresh**（慢启动阈值）：区分慢启动和拥塞避免的分界线

## 阶段一：慢启动（Slow Start）

```txt
cwnd 初始值 = 初始拥塞窗口（由实现与配置决定）
每个确认新数据的 ACK 最多增加约 1 MSS（具体按已确认字节和实现）
在持续有数据、确认节奏正常的简化条件下，每 RTT 近似翻倍

1 → 2 → 4 → 8 → 16 ...（直到 cwnd ≥ ssthresh）
```

名字叫"慢"，实际是**指数增长**，只是相比"一下子打满"更慢。

## 阶段二：拥塞避免（Congestion Avoidance）

```txt
当 cwnd ≥ ssthresh：
经典 Reno 近似每 RTT 增长 1 MSS；逐 ACK 的实现采用字节计数等规则
```

增长放缓，探测网络上限。

## 阶段三：快重传（Fast Retransmit）

```txt
经典 Reno 用 3 个重复 ACK 作为丢失信号，提前重传疑似丢失段
不等超时计时器，减少等待时间
```

重复 ACK 也可能由乱序或复制产生；现代 RACK-TLP 可利用时间与 SACK 信息检测丢失，不应把“3 个重复 ACK”当作所有 TCP 栈唯一的快重传条件。

## 阶段四：快恢复（Fast Recovery）

触发快重传后（收到 3 个重复 ACK）：

```txt
ssthresh 按在途数据量约减半，并受最小值约束
经典 Reno 在第 3 个重复 ACK 时暂设 cwnd = ssthresh + 3*MSS
收到确认恢复数据的 ACK 后，再把 cwnd 收回到 ssthresh
```

对比超时（RTO）触发时：

```txt
ssthresh 依规范缩减；cwnd 回到 loss window，经典模型约为 1 MSS
```

## 事件顺序（示意）

```text
有数据可发 → 慢启动近似指数增窗 → 到阈值后 Reno 近似线性增窗
疑似丢失 → 快重传/恢复，缩小拥塞窗口并保持 ACK clock
重传超时 → 更保守地缩窗，重新探测可用容量
```

# CUBIC 与 BBR（现代拥塞控制）

|算法|特点|
|---|---|
|Reno（经典）|基于丢包，收到 3 dup ACK 或超时才降速|
|CUBIC（许多 Linux 环境常见）|基于丢包，用三次函数增长，适合较大带宽时延积场景；实际默认算法取决于内核与配置|
|BBR（带宽/RTT 模型）|估计瓶颈带宽与最小 RTT，行为取决于版本、队列和竞争流；不能断言任何随机丢包网络都更好|

[RFC 5681: TCP Congestion Control](https://www.rfc-editor.org/rfc/rfc5681.html) · [RFC 8985: RACK-TLP](https://www.rfc-editor.org/rfc/rfc8985.html)
