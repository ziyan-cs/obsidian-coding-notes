# TCP/IP 分层与数据传输

> [!note] 本节重点：OSI 七层与 TCP/IP 四层对比、数据封装与解封装流程、IP/端口/MAC 协作寻址、DNS 解析流程

## 层级关系

| OSI 七层 | TCP/IP 四层 | 作用             | 相关协议/设备                |
| ------ | --------- | -------------- | ---------------------- |
| 应用层    | 应用层       | 面向用户的应用服务      | HTTP/HTTPS、FTP、DNS、SSH |
| 表示层    | -         | 数据格式转换、加密解密    | SSL/TLS                |
| 会话层    | -         | 建立/维护/终止会话     | RPC、NetBIOS            |
| 传输层    | 传输层       | 端到端数据传输、端口寻址   | TCP、UDP                |
| 网络层    | 网络层       | 路由寻址、跨网段传输     | IPv4/IPv6、ICMP；ARP/邻居发现衔接下一跳 |
| 数据链路层  | 链路层       | 帧传输、MAC寻址、差错检测 | 以太网、交换机、PPP            |
| 物理层    | -         | 比特流传输、物理介质     | 网线、网卡、集线器              |

## 核心区别

- OSI 七层是教学参照，不是每种协议都必须严格落在一格；TLS、DNS 和隧道协议常跨越简化边界。
- TCP/IP 四层是便于排障的模型，不代表真实报文永远只有四个固定头部；IPv6 扩展头、VLAN、隧道和 NAT 都会改变路径。

## 数据封装与传输流程

> 数据在网络中传输的本质：**发送端逐层封装，接收端逐层解封装** 
## 发送端（封装）

每一层为数据加上本层的头部，向下传递：

| 步骤  | 层级  | 操作                    | 产物        |
| --- | --- | --------------------- | --------- |
| 1   | 应用层 | 生成原始数据（如 HTTP 请求）     | 数据 Data   |
| 2   | 传输层 | 加 TCP/UDP 头部（端口号、序列号） | 段 Segment |
| 3   | 网络层 | 加 IP 头部（源/目标 IP 地址）   | 包 Packet  |
| 4   | 链路层 | 加 MAC 头部（源/目标 MAC 地址） | 帧 Frame   |
| 5   | 物理层 | 转为比特流，通过网线/电磁波发送      | 位 Bit     |

## 接收端（解封装）

从下到上逐层剥去头部，还原原始数据：

物理层 → 链路层（剥 MAC 头）→ 网络层（剥 IP 头）→ 传输层（剥 TCP/UDP 头，校验数据）→ 应用层（应用程序读取）
## 关键概念

- 封装：每层为数据加上自己的头部信息
- 解封装：接收端逐层去掉头部，还原原始数据
- PDU：每一层的数据单位，传输层叫「段」，网络层叫「包」，链路层叫「帧」

# 地址与端点标识
## IP 地址 / 端口号 / MAC 地址

> 三者分别回答不同的寻址问题：**去哪台机器 → 哪个进程 → 下一跳谁收**

## 基础定义

- IP 地址通常标识网络接口或可路由端点，不必与一台物理机器一一对应；私网地址、NAT、负载均衡和 anycast 都会改变“一个 IP = 一台主机”的直觉。
- TCP/UDP 端口参与区分传输端点，内核再根据地址、端口、协议和 socket 状态分发；一个端口并不总对应唯一进程。
- 以太网 MAC 用于本链路帧交付，可被软件配置，不一定是不可变的“烧录地址”；并非所有链路技术都用以太网 MAC。

## 三者协作：以访问一个网站为例

```txt
用户输入 URL
    ↓
应用层：构造 HTTP 请求，目标端口 80/443
    ↓
传输层：TCP 封装，携带【源端口 + 目标端口】
    ↓
网络层：IP 封装，携带【源 IP + 目标 IP】，负责跨网段路由
    ↓
链路层：MAC 封装，携带【源 MAC + 下一跳 MAC】，负责本段投递
    ↓
每经过一个以太网路由跳：链路层帧重新封装，下一跳 MAC 改变；IP 源/目的通常保持，但 TTL/Hop Limit 会变化，NAT 或隧道还可能改写地址/封装
    ↓
到达目标主机：逐层解封装，最终交给对应端口的进程
```

## 关键对比
| 特性    | IP地址      | 端口号        | MAC地址       |
| ----- | --------- | ---------- | ----------- |
| 解决的问题 | 跨网段定位设备   | 定位设备上的应用进程 | 局域网内定位设备    |
| 作用范围  | 路由域内或公网可达范围 | 受协议、地址与 socket 绑定约束 | 本链路上的帧投递 |
| 是否可改  | 可动态/静态配置  | 可动态分配      | 可由硬件提供或软件配置 |
| 对应层级  | 网络层       | 传输层        | 链路层         |

# DNS 解析与缓存

> 核心：递归查询vs迭代查询、解析流程、缓存机制

DNS 是分布式命名系统，不只返回 IP：`A/AAAA` 提供地址，`CNAME` 表示别名，`MX/TXT` 等承担其他用途。解析器最终如何选用地址，还受客户端策略、缓存和网络环境影响。

## 查询方式

- 递归查询：客户端只问一次本地 DNS，由本地 DNS 代为查询到底，最终返回结果
- 迭代查询：本地 DNS 一层层向上询问，每次只得到下一级服务器的地址，自行继续追问

## 典型解析流程（不是固定软件执行顺序）

```txt
用户输入域名
    ↓
1. 应用/系统按自身配置查询 hosts、缓存或解析服务
    ↓（本地无法回答）
2. 向递归解析器发送查询（也可能使用 DoH/DoT）
    ↓
3. 递归解析器按需询问根服务器 → 得到顶级域的委派信息
    ↓
4. 顶级域名服务器（如 .com）→ 得到权威服务器委派信息
    ↓
5. 权威服务器 → 返回所请求的资源记录或否定回答
    ↓
6. 解析器按记录 TTL 与本地策略缓存结果，返回给客户端
    ↓
客户端根据地址选择、路由与应用协议发起后续连接
```

## DNS 缓存

递归解析器和客户端可按 TTL 与实现策略缓存正向或否定结果；权威服务器是数据来源，不应笼统说“每一层都会缓存”。排障时分别检查 hosts、客户端缓存、递归解析器与权威记录，不能仅凭一次 `ping` 判断 DNS 正确。

[RFC 8499: DNS Terminology](https://www.rfc-editor.org/rfc/rfc8499.html) · [RFC 8200: IPv6](https://www.rfc-editor.org/rfc/rfc8200.html)
