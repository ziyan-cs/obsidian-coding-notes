# 先定义负载与通过条件

## 压测指标

记录路由、请求体、数据集大小、缓存冷热比例、客户端与服务端机器、TLS/HTTP 版本、并发连接数、目标到达率、预热和持续时间。吞吐是**完成的成功请求数/秒**；延迟的起止点要写清楚，P50/P95/P99 需与错误率和超时数量一起看。连接数不是在途请求数（HTTP/2 可复用并多路复用）。

先定义服务级通过条件，例如“在给定到达率下，错误率低于某阈值且 P99 低于业务预算”；阈值来自业务需求，不从别人的笔记抄固定百分比。除了客户端结果，还要同步采集 CPU、内存、连接池等待、队列长度、数据库和 Redis 延迟。

# 用 wrk 做第一轮实验

`wrk` 以线程和连接数产生闭环负载：响应变慢时，固定连接上的后续请求也可能变少，因此其延迟分布可能漏掉停顿期间本应到达的请求（coordinated omission）。它适合快速摸索容量，不足以单独证明固定到达率下的尾延迟。

```bash
wrk -t2 -c20 -d30s --latency http://127.0.0.1:8080/
```

要发 POST，先创建 `post.lua`（脚本内容与终端命令分开）：

```lua
wrk.method = "POST"
wrk.body = '{"key":"value"}'
wrk.headers["Content-Type"] = "application/json"
```

```bash
wrk -t2 -c20 -d30s --latency -s post.lua http://127.0.0.1:8080/api
```

不要对未授权的公网目标压测。需要固定请求到达率与更可靠的尾延迟时，换用明确支持该模型的工具，例如 `wrk2 -R`，并记录其版本与配置；压测器本身也可能先到瓶颈。

## 性能瓶颈定位流程

```
1. 小负载验证返回码、响应内容和数据是否正确，另做预热。
2. 逐级增加连接数或目标到达率，每级保持足够长的稳定观察窗口；记录成功吞吐、P95/P99、超时、排队和依赖负载。
3. 发现吞吐不再增加或尾延迟/错误率陡升时，先排除客户端 CPU、端口、连接数和网络限制。
4. 对服务端收集 `top`/`vmstat`、`ss -s`、应用指标；按疑点用 `perf`、`iostat`、数据库慢查询或采样 trace 定位，不在繁忙生产实例上无预算地全量 `strace`。
5. 改一处瓶颈后在相同数据、版本和负载模型下复测，保留原始命令及输出。
```

# ab：只作简单对照

```bash
ab -n 1000 -c 10 http://127.0.0.1:8080/
```

`ab` 可用于最小 HTTP/1.x 对照，不应拿它的默认行为代表 HTTP/2、多路复用或复杂生产流量。工具之间的请求模型不同，结果不能只按 QPS 排名。

## 常见问题与分析方法

| 现象 | 可能原因 | 验证方法 | 解决方向 |
|------|---------|---------|---------|
| 成功吞吐低、CPU 空闲 | 依赖等待、锁、限流或压测器不足 | 分段耗时、队列、客户端资源 | 先确定等待发生在哪一层 |
| 吞吐上不去且错误增加 | fd/连接池/端口/内存限制 | 错误码、`ss`、池等待与资源上限 | 修正约束或过载策略并复测 |
| P50 稳定、P99 升高 | 排队、GC、锁、慢依赖等 | trace/采样 profile 与队列曲线 | 找到与尾延迟同一时间窗的证据 |
| 上下文切换上升 | 线程过多、阻塞唤醒等 | `vmstat`、调度采样 | 区分正常负载增长和无效切换 |

## 压测注意事项

1. **压测客户端不能成为瓶颈**：wrk 客户端本身需要足够资源
2. **预热阶段**：独立预热缓存、连接池与页面缓存，正式计量窗口不混入启动效应
3. **避免同机压测**：客户端和服务端互相影响
4. **长时间压测**：短时压测无法发现内存泄漏
5. **关注错误率**：QPS 再高，有错误也没意义
6. **不要只看平均延迟**：P99 与平均值的比例没有通用常数；看原始分布与超时截断

> [!tip]- **工程要点**：选择运行点应满足业务延迟、错误率和故障余量目标，而不是直接把“拐点并发数”或固定 30–50% 余量设为生产配置。流量峰值、自动扩缩容时延、单实例故障后的剩余容量都要进入容量计划。
