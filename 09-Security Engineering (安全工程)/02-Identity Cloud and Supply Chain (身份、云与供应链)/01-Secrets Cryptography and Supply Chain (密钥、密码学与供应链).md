> [!abstract] 学习目标
> 密钥、配置与依赖都具有生命周期。安全交付要求秘密不进入代码和镜像，进程只获得最小权限，依赖来源可追踪，并能在泄漏或漏洞发生后完成轮换、回滚和审计。

# Secrets 生命周期

Secret 包括数据库密码、API token、私钥、签名密钥和云凭据。它们需要经过创建、分发、使用、轮换、撤销和销毁，而不是“放进环境变量就结束”。

基本原则：

- 不写入源码、Git 历史、镜像层、测试快照或日志。
- 不同环境、服务和用途使用不同凭据，限制权限和有效期。
- 运行时通过 secret manager、受控挂载或平台身份获取，启动日志只记录标识和版本，不记录值。
- 轮换需要重叠窗口：先让消费者接受新旧凭据，再切换生产者，最后撤销旧凭据。
- 一旦怀疑泄漏，先撤销和轮换，再调查历史；仅从最新提交删除并不能清除 Git 历史。

环境变量可能被子进程、调试信息或错误报告暴露；文件挂载也需要权限、生命周期和备份边界。选择载体时应结合威胁模型，而不是认为某一种方式天然安全。

# 加密、哈希与签名

三类工具解决不同问题：

| 工具 | 目标 | 典型场景 |
| --- | --- | --- |
| 对称/非对称加密 | 保密性 | TLS、磁盘或字段加密 |
| 密码哈希 | 抗离线猜测 | 密码存储 |
| MAC / 数字签名 | 完整性与来源 | token、webhook、软件制品 |

不要自行设计密码协议。使用成熟库与现代 AEAD，明确 nonce/IV 的唯一性要求、密钥版本和认证失败处理。Base64 只是编码，不提供保密性；哈希也不等于加密。

TLS 保护传输链路，但不会自动解决服务端越权、日志泄密、客户端被攻陷或数据库明文访问。证书校验必须验证信任链与目标主机名，内部服务也不能用“内网可信”跳过认证。

# 最小权限与隔离

- 服务账户只拥有必要数据库表、队列 topic、对象存储路径和云 API 权限。
- 普通服务进程不以 root 运行；容器删除不需要的 Linux capabilities，文件系统尽量只读。
- 管理面与数据面分离；调试接口、metrics、profiling 和管理端口不直接暴露公网。
- 网络策略与防火墙限制东西向访问，应用仍需做身份与授权检查。
- 日志避免凭据、完整 token、密码、支付信息和不必要的个人数据，并设置访问与保留策略。

# 依赖与构建供应链

依赖风险不仅是公开漏洞，还包括拼写投毒、恶意维护者、构建脚本执行和镜像来源不明。

交付基线：

1. 使用锁文件或可复现机制固定直接与传递依赖。
2. 从可信 registry 获取依赖和基础镜像，必要时验证签名与摘要。
3. 生成 SBOM，持续扫描依赖和镜像；扫描结果必须进入修复流程，而不是只生成报告。
4. 构建凭据采用短期权限，不把 token 留在镜像层或 CI 日志。
5. 发布制品可追溯到源码版本、构建环境和流水线；部署支持快速回滚。
6. 漏洞修复同时评估可利用性、暴露面、补丁风险和临时缓解，不只看 CVSS 数字。

# 事故响应自测

- [ ] Git 历史出现云密钥后，能否立即撤销、轮换并查清使用记录？
- [ ] 签名密钥轮换时，验证端能否在过渡期识别 key ID 并接受两代密钥？
- [ ] 第三方依赖出现高危漏洞时，能否定位哪些制品和环境实际受影响？
- [ ] 服务被入侵后，它的账户和网络权限能否限制横向移动？
- [ ] 日志和审计记录是否足以回答谁在何时访问或修改了敏感资源？

> [!summary] 核心摘要
> 从一个数据库密码的创建开始，说明它如何进入服务、怎样限制权限、如何轮换、怎样避免进入日志和镜像，以及泄漏后如何撤销并审计影响。
