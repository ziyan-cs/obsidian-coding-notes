> 威胁驱动检测、日志语义与证据保全统一见 [Security Detection and Incident Evidence (安全检测与事件证据)](/02-Engineering%20Fundamentals%20(工程基础)/03-Verification%20and%20Diagnostics%20(验证与诊断)/06-Security%20Detection%20and%20Incident%20Evidence%20(安全检测与事件证据).md)；本篇聚焦安全事件源、规则运营和响应联动。

> [!abstract] 学习定位
> 安全控制无法保证永不失守；日志、检测和响应流程决定异常能否在影响扩大前被发现并限制。

> [!summary] 核心摘要
>
> 审计事件记录谁在何时对什么资源执行了什么结果，并保证时间、身份和关联 ID 可追踪。响应先控制影响和保存证据，再恢复服务与分析根因。

# 应记录的安全事件

- 登录、会话创建、撤销和高风险认证变化。
- 权限变更、角色绑定、密钥创建与敏感数据访问。
- 管理操作、策略拒绝、限流、异常出网和部署变更。
- 关键业务状态转换与人工审批。

不要记录明文密码、token、私钥和不必要的个人数据。日志读取权限也必须受控。

# 事件模型与检测

结构化字段至少包含时间、actor、action、resource、result、source、request/trace ID 与稳定错误码。服务之间同步时间并统一身份标识，才能还原调用链。

一条“跨租户订单读取被拒绝”事件可以记录 `actor_id`、`tenant_id`、`action=order.read`、资源类型与脱敏 ID、`result=deny`、策略版本、request ID 和 UTC 时间。不要记录订单全文或完整 bearer token。检测规则再把“同一主体短时间内反复访问不同租户资源”作为可调查线索，而非仅凭一次拒绝就判定入侵。

检测规则应对应威胁：异常失败、高频权限拒绝、服务身份访问新资源、容器异常启动 shell。阈值以基线和风险调整，避免告警风暴。

# 响应过程

~~~text
detect -> triage -> contain -> preserve evidence
       -> eradicate -> recover -> verify -> learn
~~~

控制措施可能包括撤销凭据、隔离工作负载、阻断流量或回滚版本。操作必须记录时间线和负责人；不要在保留证据前随意清理现场。

恢复后要区分触发事件、促成条件和根因，形成可验证的长期修复，并确认类似资产是否受影响。

# 规则即代码与数据健康

每条规则保存威胁假设、数据源、查询、严重度、已知误报、处置步骤、测试样本和 owner。测试同时包含攻击样本、正常高峰和字段缺失；schema 变化或采集停止要触发独立健康告警，不能表现为“攻击消失”。

调查先保留原始事件，再按 UTC 时间线关联身份、资源、部署和 trace。区分事实、推断与未知，记录查询和过滤范围。高价值审计流远程传输并限制删除权限，普通采样策略不得随机丢弃安全事件。

运行指标包括数据延迟/缺失、解析失败、规则命中与误报、确认时间和未分配告警。一次演练从攻击动作走到告警、分诊、隔离和证据包，才能证明规则可运营。

# 可执行准备

为账号泄露、密钥泄露、恶意镜像、越权访问和数据泄漏准备运行手册。演练要验证联系人、权限、备份、回滚和日志查询真实可用。
