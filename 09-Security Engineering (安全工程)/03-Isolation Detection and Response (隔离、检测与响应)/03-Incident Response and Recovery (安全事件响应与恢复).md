> [!note] 方法论坐标
> 检测质量与事件证据统一见 [Security Detection and Incident Evidence (安全检测与事件证据)](/02-Engineering%20Fundamentals%20(工程基础)/03-Verification%20and%20Diagnostics%20(验证与诊断)/06-Security%20Detection%20and%20Incident%20Evidence%20(安全检测与事件证据).md)；本篇聚焦确认事件后的隔离、根除、恢复与沟通。

> [!abstract] 学习定位
> 事件响应的首要目标是限制业务与数据损失，同时保存足以判断范围和根因的证据；恢复不是“服务能启动”，而是确认攻击路径被关闭、数据可信、风险回到可接受水平。

> [!summary] 核心摘要
>
> 先分级并建立指挥，再止损和保全证据；根除后分阶段恢复，用日志、指标、数据校验和业务验证证明安全，最后把发现转化为有负责人和截止条件的改进项。

# 准备与分级

响应能力必须在事故前准备。至少明确值班入口、事件指挥官（Incident Commander）、技术处置、沟通、记录和业务决策职责，并为账号接管、密钥泄漏、恶意发布、数据泄露与勒索准备运行手册。

分级依据应包含影响范围、数据敏感度、攻击者是否仍活跃、关键业务中断程度以及法律或客户通知义务。严重度用于决定响应速度与资源，不代表根因难度。

首次报告需要回答：发现了什么、证据来自哪里、可能影响什么、当前是否仍在扩大、下一次更新时间。未知项明确标为未知，不用猜测填满报告。

# 止损与证据保全

止损策略需要权衡攻击扩散与业务连续性：可撤销 token、轮换密钥、冻结账号、隔离实例、阻断出口、回滚发布或临时关闭功能。高风险操作由指挥角色批准并记录时间、操作者、原因和结果。

证据保全遵循可追溯原则：保存原始日志、告警、审计记录、部署记录、内存或磁盘快照及关键查询结果；统一时间基准并计算完整性校验。不要为了“清理现场”立即重启、删文件或覆盖日志。

止损与保全不必机械串行：如果泄漏密钥仍能访问生产，应立即限制或撤销它，同时由另一人保全访问日志、记录撤销时间和可能失去的现场信息。等待“取证完整”而放任攻击继续，同样是失败的响应决策。NIST SP 800-61 Rev. 3 强调把准备、检测、响应和恢复融入持续风险管理，具体操作顺序应由当前风险决定。

必须并行确认攻击者可能获得的身份。隔离一台主机但保留已泄漏的云凭据，攻击者仍可从其他入口继续活动。

# 根除与范围确认

区分三个问题：触发事件是什么、哪些控制失效促成扩大、攻击者还留下了哪些持久化手段。修补单个漏洞并不自动消除被创建的账号、恶意密钥、后门任务或被污染的制品。

范围确认从已知指标扩展：同一身份访问过哪些资源，同一制品部署到哪些环境，同一攻击特征是否出现在其他日志，哪些数据可能被读取或修改。查询过程本身要保存，便于复核结论。

# 恢复与安全验证

恢复采用分阶段放量：从可信源码和制品重建，恢复必要配置与数据，先在隔离环境验证，再小流量上线。持续观察认证、权限拒绝、异常出网、错误率、延迟和数据一致性。

恢复完成至少需要以下证据：攻击入口已关闭；泄漏凭据已撤销而非仅新增；持久化机制已清除；数据与备份通过校验；关键业务路径正常；检测能够识别同类行为；回退方案仍可用。

若使用备份，需要确认恢复点早于污染时间，并验证 RPO/RTO。复制会同步逻辑删除或破坏，因此副本不是备份。

# 沟通与复盘

内部更新保持固定节奏，区分事实、假设、决策与待办。对外沟通由授权角色统一发布，内容应准确描述影响、处置和用户行动，避免未经证实的归因。

复盘关注系统条件而非寻找替罪者：时间线、影响、发现方式、控制为何失效、哪些动作有效或拖慢恢复。行动项必须有负责人、优先级、完成条件和验证方式；“加强意识”不是可验收改进。

# 桌面演练

以“生产服务账号密钥出现在公开仓库”为场景演练：

1. 如何确认密钥是否有效、何时暴露、被谁使用过？
2. 先撤销还是先采集证据，怎样把两者并行而不扩大风险？
3. 哪些服务依赖该凭据，轮换怎样避免引发第二次事故？
4. 如何查询跨账号、跨区域和第三方系统的访问范围？
5. 用什么证据宣布恢复，并防止同类秘密再次进入仓库？

> [!question]- 理解检查
> 某服务修补漏洞并恢复了流量，但没有轮换凭据、检查持久化账号或验证数据完整性。为什么这仍不能称为恢复完成？
