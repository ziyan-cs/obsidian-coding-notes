> [!abstract] 学习目标
> 把“注意安全”转化为可追踪、可测试、可留证的工程要求。风险清单用于发现方向，ASVS 等验证标准用于定义控制是否真正存在；扫描器只能提供部分证据。

> [!summary] 核心摘要
>
> 安全需求应绑定资产、威胁、控制和验证证据：谁要保护什么，攻击者如何越过信任边界，系统在哪一层阻断，测试怎样证明成功与失败路径。Top 10 是意识清单，不是完整验收标准。

# 从威胁到可验证要求

一条安全要求至少包含：

```text
asset + actor + trust boundary
  -> abuse case
  -> preventive / detective / recovery control
  -> verification method and evidence
```

例如“订单只能由所属租户读取”应拆为：租户身份来自可信凭据；查询必须包含 tenant scope；缓存键包含租户；管理员跨租户访问单独授权并审计；测试覆盖他人 ID、批量接口、导出、缓存命中和后台任务。只写“防止越权”无法指导实现与验收。

# 使用 ASVS 而不是照抄清单

OWASP ASVS 提供 Web 应用安全控制的验证要求。项目应先根据数据敏感度、暴露面和业务影响选择适当验证深度，再将相关要求映射到设计、代码、配置和测试。

| 领域 | 后端应留下的证据 |
| --- | --- |
| 架构与威胁建模 | 数据流图、信任边界、滥用场景、风险接受记录 |
| 认证与会话 | issuer/audience 校验、过期撤销、会话固定与重认证测试 |
| 访问控制 | 对象/字段/功能负向矩阵、默认拒绝、跨租户测试 |
| 输入与输出 | schema、参数化查询、上下文编码、文件与反序列化限制 |
| 密码学与秘密 | 算法/协议选择依据、密钥生命周期、轮换和泄漏演练 |
| 日志与错误 | 安全事件字段、隐私脱敏、完整性、告警与调查流程 |
| API 与资源 | 速率、配额、分页、批量、超时和高成本业务流限制 |

引用具体要求时记录 ASVS 版本，因为章节和编号会演进。不要声称“通过 Top 10”就代表应用安全；风险优先级仍取决于业务和威胁模型。

# 验证手段的边界

- SAST 擅长发现部分危险数据流和 API 用法，但难以理解完整业务授权。
- DAST 从外部观察运行系统，受测试覆盖、身份和环境数据限制。
- SCA/SBOM 识别已知依赖风险，不证明依赖在当前路径可利用，也不发现业务漏洞。
- fuzzing 擅长解析器、状态机和边界输入，需要有效 oracle、语料和崩溃去重。
- code review 与架构评审能发现设计和业务问题，但必须有明确检查目标和复现实证。

工具结果应经过确认、分级和去重。修复完成要加入回归测试；不能复现或接受的风险也要记录范围、依据、到期时间和负责人。

# 发布门禁与例外

门禁按风险而不是告警数量设计：高危凭据泄漏、可利用远程执行、跨租户越权应阻断发布；低置信度或无可达路径的依赖告警可以进入限时处置流程。例外不是永久忽略，必须包含补偿控制和复查时间。

最低发布证据可包含：

1. 威胁模型和本次变更影响。
2. 权限与输入边界的自动化负向测试。
3. 依赖、镜像、Secret 和 IaC 扫描结果。
4. 关键安全配置的运行时验证。
5. 未解决风险、所有者和处置期限。
6. 回滚、吊销和事件响应入口。

# 实践任务

选择一个含登录、订单查询、文件上传和 Webhook 的 API，建立 15～25 条项目相关的安全要求。每条关联至少一个自动化测试或人工验证步骤，并保存最小证据。最后注入一个对象越权和一个 SSRF 缺陷，证明门禁或测试能在发布前发现。
