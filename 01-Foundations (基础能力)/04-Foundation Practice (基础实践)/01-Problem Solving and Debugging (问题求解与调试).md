> [!abstract] 学习目标
> 把“程序不对”转成可复现、可观测、可证伪的问题；能够使用终端、日志、调试器、sanitizer 和系统工具逐层定位根因。

# 调试是一套证据流程

可靠的问题定位遵循：

```text
描述症状 → 稳定复现 → 缩小变量 → 提出假设
        → 设计可证伪实验 → 定位根因 → 修复
        → 回归验证 → 记录可迁移经验
```

症状是“请求超时、进程崩溃、答案错误”；根因可能是锁顺序、越界、配置、输入或下游。不要把第一条异常日志直接称为根因。

# 建立可复现样本

一份有效复现至少记录：

- 代码版本、构建类型、编译器/运行时版本；
- 操作系统、架构、依赖和关键配置；
- 输入数据、执行命令、期望结果与实际结果；
- 是否稳定复现，概率和触发前置条件；
- 第一次已知正常版本与第一次异常版本。

把输入、线程数、数据规模或依赖逐步缩小，寻找仍能触发问题的最小样本。最小化不是为了让代码好看，而是减少可能原因并加快实验反馈。

# 从输入到系统逐层检查

## 程序与数据层

1. 输入是否满足接口前提？
2. 边界、长度、编码、单位和所有权是否一致？
3. 哪个不变量最早被破坏？
4. 错误发生在计算、状态更新还是输出转换？

优先在不变量附近加入断言，而不是到处打印变量。断言用于发现“不应该发生”的程序错误，不应用来处理合法外部输入。

## 进程与系统层

```bash
ps -ef
ps -eLf
top
pidstat -p <pid> 1
cat /proc/<pid>/status
cat /proc/<pid>/limits
lsof -p <pid>
ss -lntp
```

观察 CPU、线程、文件描述符、内存和连接时，要保存时间点和命令参数。容器内看到的 namespace/cgroup 视图可能与宿主机不同。

# 日志与可观测性

日志应回答“何时、哪个请求、哪个组件、发生了什么”，并携带结构化字段：时间、级别、request/trace ID、关键状态和错误分类。不要记录密码、令牌、完整隐私数据或无界请求体。

- log 用于离散事件和上下文；
- metric 用于聚合趋势、速率和分布；
- trace 用于跨组件因果路径；
- profile 用于资源消耗位置。

相关性不是因果。看到 CPU 与延迟同时上升，只能形成假设；还要通过时间顺序、对照实验或更细证据验证。

# C++ 调试工具链

## 编译出可诊断程序

```bash
c++ -std=c++20 -g -O1 -Wall -Wextra -Wconversion program.cpp
```

调试构建保留符号；优化级别会影响变量可见性与执行顺序。问题只在 release 出现时，不应简单改成 `-O0` 后宣布消失，而应在接近生产优化下保留符号并分析。

## Sanitizer

```bash
# 地址越界、use-after-free、部分内存错误
c++ -g -O1 -fsanitize=address,undefined program.cpp

# 数据竞争；通常单独构建，不与 ASan 混用
c++ -g -O1 -fsanitize=thread program.cpp -pthread
```

Sanitizer 会改变时序和内存布局；未报告不等于没有错误，报告也要追到首次非法操作而非最后崩溃点。

## 调试器

GDB/LLDB 的核心动作：设置断点、单步、查看调用栈、切换栈帧、检查变量与内存、设置条件断点和观察点。崩溃时先保存 core dump 与对应二进制/符号，再分析：

```text
bt / thread apply all bt
frame N
info locals
print expression
```

调用栈是当时控制流证据，不自动指出根因；内存破坏常在更早位置发生。

# 系统调用与性能问题

```bash
strace -f -tt -T -o trace.log ./program
perf stat ./program
perf record -g ./program
perf report
```

`strace` 适合判断在等文件、网络、锁相关 futex 还是不断失败重试；`perf` 适合 CPU 事件和热点。工具本身有开销，生产使用前先评估采样频率和数据敏感性。

# 假设驱动排查

维护一张简表：

| 假设 | 支持证据 | 反对证据 | 下一实验 |
|---|---|---|---|
| 连接池耗尽 | 等待线程多、池 in-use 达上限 | DB 延迟稳定 | 临时降低入口并发，观察等待 |

每次实验尽量只改变一个主要变量。若结果不能区分两个假设，就不是有效实验。二分版本、二分输入、替换依赖和故障注入都属于缩小因果范围的方法。

# 根因与修复验收

修复必须回答：

1. 哪个机制导致症状？
2. 为什么现有防线没有拦住？
3. 修改如何破坏故障链？
4. 哪个回归测试能在旧代码失败、新代码通过？
5. 是否引入性能、兼容性或可观测性副作用？

# 检查理解

1. 为什么复现概率和环境信息属于问题定义，而不是附加信息？
2. Sanitizer 没有报警为什么不能证明程序安全？
3. 日志、指标、链路和 profile 分别回答哪类问题？
4. 怎样设计一个能证伪“数据库变慢导致超时”的实验？

> [!summary] 本篇结论
> 调试不是凭经验猜测，而是不断缩小可疑集合的证据过程。复现、最小化、不变量、工具观测和可证伪实验共同把症状推进到根因。
