> [!abstract] 学习目标
> 从契约和风险设计测试，掌握等价类、边界值、性质测试、模糊测试与并发验证，并知道测试能证明什么、不能证明什么。

# 测试从契约开始

测试不是为代码行寻找输入，而是验证可观察契约：

```text
前置条件：允许什么输入和环境？
操作：调用什么接口？
后置条件：返回值、状态变化和副作用是什么？
不变量：操作前后始终必须成立什么？
失败语义：错误如何报告，是否可重试？
```

没有清晰 oracle（判定对错的方法），测试只能执行代码，不能可靠验证行为。

# 测试层次

| 层次 | 主要验证 | 优势 | 局限 |
|---|---|---|---|
| 单元测试 | 小组件与纯逻辑 | 快、定位精确 | 可能脱离真实集成 |
| 组件/集成测试 | 数据库、网络、文件等协作 | 发现接口与配置问题 | 环境和数据管理较复杂 |
| 端到端测试 | 用户路径与整体部署 | 接近真实行为 | 慢、失败定位困难 |
| 性能/可靠性测试 | 延迟、吞吐、容量、故障恢复 | 验证非功能要求 | 需要稳定环境和统计分析 |

健康测试组合通常是大量快速小测试、适量集成测试和少量关键端到端测试，而不是追求某一层覆盖全部风险。

# 输入空间划分

## 等价类与边界值

把行为相同的输入分为等价类，每类选代表；再重点测试边界两侧：

- 空、单元素、最小/最大允许长度；
- `limit-1`、`limit`、`limit+1`；
- 重复值、已排序、逆序、全相等；
- 零、负数、整数极值与溢出附近；
- 合法/非法编码、缺字段、额外字段；
- timeout 前、恰好 timeout、timeout 后。

组合条件过多时，可按风险选择 pairwise 或决策表，而不是暴力枚举所有笛卡尔积。

## 状态机测试

对连接、事务、订单等对象，列出合法状态与迁移：

```text
Created → Running → Succeeded
                  ↘ Failed
Running → Cancelled
```

测试不仅覆盖合法路径，还应拒绝非法迁移、重复操作和乱序消息，并验证幂等性。

# 性质测试与差分测试

性质（property）比单个样例更一般：

- 排序后序列非降，且元素多重集合不变；
- 编码后解码得到原值；
- 集合并满足交换律和幂等律；
- 序列化结果再次序列化保持稳定。

性质测试框架生成大量输入并在失败后 shrink 到较小反例。差分测试则把待测实现与可靠参考实现或另一独立实现比较，适合算法、解析器和协议实现。

# Fuzzing 与 Sanitizer

Fuzzer 持续生成/变异输入，以覆盖率反馈寻找新路径。它擅长发现崩溃、越界、断言失败和解析器边界；若程序没有有意义的断言或 oracle，逻辑错误可能静默存在。

将 fuzzing 与 ASan/UBSan 结合能提高内存错误发现率。语料应包含真实格式种子；崩溃输入必须保存、最小化并转成永久回归测试。

# 并发与时间相关测试

并发 bug 依赖调度组合，重复运行通过不能证明正确。策略包括：

- 用 ThreadSanitizer 检测数据竞争；
- 在关键步骤插入 barrier/latch，构造指定交错；
- 使用虚拟时钟或可注入 clock，避免真实 sleep；
- 对取消、超时、重试、关闭和部分失败做状态机测试；
- 运行压力测试并保存随机种子。

测试不得依赖线程完成顺序、机器速度或墙上时钟的偶然值。flaky test 是产品信号，应修复不确定来源，不能简单无限重跑掩盖。

# Mock、Fake 与真实依赖

- mock 验证交互，可快速模拟错误，但容易耦合实现细节；
- fake 提供简化但有行为的实现，例如内存存储；
- 真实依赖最接近生产，但启动慢、隔离成本高。

只有 mock 的测试可能在真实 SQL、序列化、事务和网络行为上失真。关键边界应保留契约测试或真实集成测试。

# 覆盖率与变异测试

行/分支覆盖率说明哪些代码执行过，不说明断言有效，也不证明需求完整。高覆盖率仍可能遗漏并发交错、错误 oracle 和未实现需求。

变异测试主动修改运算符、条件或返回值；若测试仍全部通过，说明断言可能没有约束这段行为。覆盖率适合发现明显空白，变异测试更接近检查测试敏感度。

# 一个完整测试记录

```text
风险：整数累计可能溢出
契约：输入范围与返回类型
等价类：空、普通、含负数
边界：INT_MAX、和接近 long long 上限
oracle：高精度参考实现
性质：结果与输入排列无关（若业务如此）
回归：保存最小失败输入与修复版本
```

# 检查理解

1. 为什么代码覆盖率高不能证明测试质量高？
2. 性质测试与普通样例测试分别擅长什么？
3. mock 过多为什么可能让集成错误逃逸？
4. 如何把一次 fuzz 崩溃变成稳定的工程资产？

> [!summary] 本篇结论
> 测试质量来自契约、风险和 oracle，而不是用例数量。边界划分、性质、fuzzing、真实集成与并发控制从不同方向压缩未知行为，失败样本最终应沉淀为回归证据。
