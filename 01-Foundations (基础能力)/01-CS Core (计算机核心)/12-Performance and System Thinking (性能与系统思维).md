> [!abstract] 学习目标
> 把性能问题转换为可重复测量的假设，理解延迟、吞吐、利用率、排队与扩展性的联系，并能从现象逐层定位瓶颈。

# 性能首先是需求

“更快”不是可验收目标。先定义：

- 工作负载：请求类型、数据规模、读写比例、并发和到达模式；
- 指标：吞吐、平均与 p50/p95/p99 延迟、错误率、资源成本；
- 约束：硬件、功耗、内存、预算、一致性与可靠性；
- 基线与目标：在哪个环境、哪个版本、允许多大回归。

**延迟（latency）**是单项工作从开始到完成的时间，**吞吐（throughput）**是单位时间完成量。吞吐增加到饱和点后，队列会增长，尾延迟可能急剧恶化；CPU 未满也可能受锁、内存带宽、存储或下游服务限制。

# 三个基本模型

## CPU 时间

经典近似：

```text
CPU time = instruction count × cycles per instruction ÷ clock rate
```

它用于拆解原因，不是说 CPI 恒定。乱序执行、缓存未命中、分支预测、向量化、频率变化和并行重叠都会改变观测值。IPC 与 CPI 的关系也受“每周期/每指令如何统计”和流水线并行影响。

## Amdahl 定律

若可优化部分占原耗时比例 `p`，该部分加速 `s` 倍：

```text
speedup = 1 / ((1 - p) + p / s)
```

90% 路径加速 100 倍，总加速约 9.17 倍；即使该部分无限快，理论上限也只有 10 倍。优化后瓶颈会迁移，所以每轮都要重新测量。

## Little 定律与排队

稳定系统在口径一致时满足：

```text
L = λW
系统中平均任务数 = 平均到达/完成率 × 平均停留时间
```

例如吞吐 200 req/s、平均在系统内 50 ms，则平均约有 10 个请求在途。它不直接预测 p99，却能检查指标是否自洽。接近资源饱和时，少量抖动会形成长队列，因此生产系统通常需要余量、背压与过载保护。

# 一套可复现的性能流程

1. **定义问题**：用户症状、SLO、负载与变更范围。
2. **建立基线**：固定版本、机器、配置、数据集与运行命令。
3. **分层观测**：应用 → 运行库 → 系统调用 → 内核 → 硬件/下游。
4. **提出单个假设**：例如锁竞争导致 p99，而非“代码可能慢”。
5. **设计实验**：只改变一个主要变量，包含 warm-up 和稳定阶段。
6. **比较分布**：报告样本数、误差、多个分位数和资源利用率。
7. **验证副作用**：正确性、内存、成本、尾延迟和故障恢复。
8. **固化门槛**：保留脚本、输入和回归阈值。

微基准应防止编译器消除工作，并说明 CPU pinning、频率策略与噪声。负载生成器若“等上一个请求结束再发下一个”，可能产生 **coordinated omission**，低估服务停顿时的真实尾延迟。

# 从症状选择证据

| 现象 | 首批证据 | 下一层问题 |
|---|---|---|
| CPU 高、吞吐不升 | `top/pidstat`、`perf stat/record` | 热点、分支/缓存、锁自旋？ |
| CPU 低、延迟高 | off-CPU/线程栈、I/O 与下游指标 | 在等锁、磁盘、网络还是限流？ |
| 上下文切换高 | `pidstat -w`、运行队列 | 线程过多、锁竞争还是正常 I/O？ |
| 内存增长 | RSS/PSS、heap profile、page faults | 泄漏、缓存、碎片还是映射？ |
| p99 抖动 | 分阶段 tracing、队列深度、GC/回收 | 哪一层形成排队或暂停？ |

单一工具不能给出因果。火焰图显示样本聚集位置，不自动说明该函数可优化；CPU profile 看不到大量 off-CPU 等待；平均值会掩盖长尾。

# 扩展性与系统边界

- **并发（concurrency）**是多个任务时间上重叠，**并行（parallelism）**是同一时刻使用多个执行资源。
- 增加线程只在存在可并行工作且未撞上共享瓶颈时提高吞吐。
- 锁、共享缓存行、内存带宽、单分片数据库和下游限额都可能成为串行部分。
- 批处理可提高吞吐，却增加等待时间和失败粒度；缓存降低平均延迟，却引入一致性、容量和击穿问题。
- 水平扩展会增加网络、协调、重试和可观测性成本，不等于线性加速。

优化顺序通常是：消除不必要工作 → 改善算法与数据结构 → 批量化/局部性 → 减少竞争与 I/O → 扩展资源。每一步都以端到端指标验收。

# 实践模板

```text
问题：高峰期 /search p99 超过目标
基线：版本、实例规格、数据量、并发、持续时间
观察：CPU、运行队列、锁等待、磁盘/网络、下游延迟
假设：连接池排队是主要贡献者
实验：仅改变池大小；保持输入一致；预热后重复多轮
结果：吞吐、p50/p95/p99、错误率、资源成本
决策：接受/拒绝假设；记录回滚条件与下一瓶颈
```

# 检查理解

1. 为什么 CPU 只有 50% 仍可能已经达到系统瓶颈？
2. Amdahl 定律为什么要求优化后重新 profiling？
3. Little 定律如何检查吞吐、并发与平均延迟是否自洽？
4. 为什么只报告平均延迟和单次 benchmark 不足以决策？

> [!summary] 本篇结论
> 性能工程是“定义口径—建立基线—分层观测—验证假设—回归守护”的循环。真正的系统思维，是同时追踪工作量、队列、共享瓶颈和优化代价，而不是积累脱离环境的固定延迟数字。
