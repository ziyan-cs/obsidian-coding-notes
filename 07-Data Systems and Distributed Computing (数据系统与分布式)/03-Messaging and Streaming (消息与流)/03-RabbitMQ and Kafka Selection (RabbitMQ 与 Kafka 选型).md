> [!abstract] 学习定位：从数据真相、业务不变量和故障窗口出发，理解事务、缓存、消息与分布式协调的边界。

# 先确定消息模型，再选产品

> [!warning] 不用固定吞吐和延迟为产品贴标签
> 性能取决于消息大小、确认语义、持久化、批量、分区/队列、硬件与网络；RabbitMQ 和 Kafka 都能覆盖多种工作负载。选型先写清投递语义、重放需求、路由模型、运维能力和压测证据。

# 设计哲学对比

| 维度 | RabbitMQ | Kafka |
|------|----------|-------|
| 定位 | 消息代理（Message Broker） | 分布式流处理平台 |
| 模型 | Exchange -> Queue -> Consumer | Topic -> Partition -> Consumer Group |
| 消息保留 | 消费者确认后通常可从队列移除；未确认消息可能重投 | 日志按保留策略保存，消费位点独立推进 |
| 消费接口 | broker 递送为主，也支持客户端主动取消息 | 客户端主动 poll |
| 顺序范围 | 单队列入队有序；多消费者、重试与重投会影响业务处理顺序 | 同一分区按 offset 有序；并行处理仍须控制完成顺序 |
| 路由能力 | 灵活（direct/topic/fanout/headers） | 基于 key hash |

---

# 性能与故障边界

Kafka 的分区日志、批量与保留/重放适合事件流；RabbitMQ 的 exchange/queue 路由、确认和死信机制适合许多任务分发场景。这是功能取向，不是固定速度排名。需在同等消息大小、持久化、确认、副本、积压和消费者并发条件下测吞吐、P99 延迟与故障恢复。

# 选型指南

## 选 RabbitMQ

| 场景 | 原因 |
|------|------|
| 复杂路由 | Exchange 类型丰富 |
| 需要灵活路由/确认/死信语义 | Exchange 与 queue 模型直接表达业务路由 |
| 工作队列型订单/通知任务 | 可按路由、确认、重试与死信表达处理流程；支付仍需业务幂等与对账 |
| 灵活的死信队列 | DLX + TTL 支持 |
| 任务队列式工作负载 | 结合确认、重试、死信与消费者行为设计 |

## 选 Kafka

| 场景 | 原因 |
|------|------|
| 高吞吐日志/埋点 | 分区日志、批量与消费组适合事件流 |
| 流处理/实时计算 | Kafka Streams / Flink |
| 消息重播/回溯 | 持久化日志，可重置 offset |
| 数据管道（ETL） | 批量消费、顺序写 |
| 多下游订阅同一事件 | 各消费组独立维护位点，可在保留期内重放 |

---

选型时写一张约束表：是否要保留/重放、同键顺序的范围、重试与死信处理、投递确认与业务副作用的边界、消费者规模、运维成本。不要只凭“低延迟选 RabbitMQ、高吞吐选 Kafka”作结论。RabbitMQ 的 quorum queue 与 classic queue 行为也不同，应按所用版本核对 [RabbitMQ 队列文档](https://www.rabbitmq.com/docs/queues)；Kafka 的副本、位点与事务则见 [Apache Kafka 文档](https://kafka.apache.org/documentation/)。
