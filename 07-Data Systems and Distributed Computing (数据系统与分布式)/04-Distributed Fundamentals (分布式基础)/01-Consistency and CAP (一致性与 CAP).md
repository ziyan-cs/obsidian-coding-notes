# CAP BASE and Consistency (CAP BASE与一致性)

> [!note] 本节重点： CAP 定理（一致性/可用性/分区容错）、BASE 理论、CP vs AP 权衡、PACELC

## CAP 定理

CAP 讨论的是**发生网络分区时**的限制：若相互隔离的节点仍都要对请求给出成功响应，就无法同时保证线性一致（linearizability）。它不是“三个按钮任选两个”，更不能说某产品平时只能拥有其中两项；分区发生与否、操作种类、客户端路由和故障处理策略都要写清。

原始证明及模型边界见 [Gilbert 与 Lynch 的论文](https://groups.csail.mit.edu/tds/papers/Gilbert/Brewer2.pdf)。

```text
节点 A 与 B 失联（partition）
客户端仍可能分别向 A、B 发请求
  维持线性一致 → 至少一侧的部分操作必须等待或失败
  两侧都立即成功 → 至少某些读写无法保证线性一致
```

### 三个属性

| 属性 | 说明 |
|------|------|
| **C（Consistency）** | CAP 语境中的线性一致：每次操作看起来在调用与响应之间某一瞬间原子生效，不是“所有机器同一时刻字节完全相同” |
| **A（Availability）** | 非故障节点收到请求后最终给出非错误响应；不保证响应及时或数据最新 |
| **P（Partition Tolerance）** | 允许节点间消息被任意延迟/丢失的分区故障模型，不是一个可随意关掉的功能开关 |

### 核心洞察

分区是必须面对的故障模型；**只有分区发生时**，系统才必须在一致性与可用性之间做取舍。CAP 不是给整个产品贴永久的“CP/AP 标签”，不同读写操作可有不同语义：

```
网络分区发生时：
偏向一致性：没有多数派的一侧拒绝或挂起相关写入/线性读
  -> 客户端能否成功还取决于它能否访问多数派
  
偏向可用性：隔离两侧都可能先接受操作，再通过合并/冲突解决收敛
  -> 需要定义冲突规则与业务不变量；不是所有操作都自动“最终一致”
```

## BASE 理论

BASE 是对 CAP 中 AP 场景的延伸——"基本可用 + 软状态 + 最终一致性"：

| 要素 | 说明 |
|------|------|
| **BA（Basically Available）** | 系统出现故障时，允许损失部分可用性（如降级、限流） |
| **S（Soft State）** | 允许数据中间状态（不一致），不要求强一致性 |
| **E（Eventually Consistent）** | 经过一段时间后，数据最终达到一致 |

### ACID vs BASE

```
ACID and BASE are not opposite product categories.
  ACID: transaction properties for a defined data boundary.
  BASE: a design vocabulary often associated with availability and convergence.
  A system can use local ACID transactions and eventual consistency between services.
```

---

## PACELC 模型

CAP 只考虑了分区时的取舍，PACELC 补充了正常情况下的取舍：

```
P（分区）发生时 → 在 A（可用性）和 C（一致性）间选择
E（正常）时     → 在 L（延迟）和 C（一致性）间选择
```

```
示例应按具体操作、读写一致性设置和故障模型分析：
- 某个异步复制读路径可能偏向可用性与低延迟；
- 某个 quorum 写或线性一致读路径可能为了正确性拒绝部分请求；
- 不要只凭产品名称推导固定 CAP/PACELC 标签（VERSION_CHECK）。
```

---

> [!example]- 题型索引
> | 题型 | 要点 |
> |------|------|
> | CAP 选两个 | P 是必须的，实际在 CP 和 AP 之间选 |
> | 为什么不选 CA | 网络分区是必然的，CA 就是没有 P |
> | BASE 的本质 | 用最终一致性换可用性 |
> | ACID vs BASE | 传统单体用 ACID，分布式系统用 BASE |
> | PACELC 的 E | 正常时在延迟和一致间取舍 |
> | CP 系统举例 | ZooKeeper、etcd、HBase |
> | AP 系统举例 | Cassandra、DynamoDB、Eureka |
>

> [!tip]- **工程要点**
> CAP 不是"三选二"的静态决策，而是**可以在不同操作级别做选择**（如关键数据强一致，非关键数据最终一致）。微服务中通常 BASE 为主，仅对支付等关键操作用强一致。

>

> [!summary] 核心摘要
>
> CAP 讨论的是网络分区发生时的取舍：若要保证线性一致，某些请求可能必须失败或等待；若要持续响应，可能返回旧数据或接受稍后收敛。它不等于“平时只能选两个”，也不能用系统名字替代对具体读写路径、quorum 和故障行为的分析。

# Consistency Models (一致性模型)

> [!note] 本节重点： 一致性模型分级（强/弱/最终）、Quorum 机制、读写模型、Dynamo 风格

## 一致性模型分级

| 模型 | 说明 | 延迟 | 典型场景 |
|------|------|------|---------|
| **强一致** | 写完成后立即对所有读可见 | 高 | 银行转账、库存扣减 |
| **线性一致性** | 所有操作按全局时钟排序，最强 | 最高 | 分布式锁（etcd） |
| **顺序一致性** | 单个进程内操作有序，全局不一定 | 中 | 聊天消息 |
| **因果一致性** | 有因果关系的操作有序 | 中 | 社交网络评论 |
| **最终一致性** | 无更新后最终同意 | 低 | DNS、CDN 缓存 |
| **读己之写** | 总能读到自己的写入 | 低 | 用户资料更新 |
| **单调读** | 后续读不会看到更旧的值 | 低 | 绝大多数应用 |

## Quorum 机制

N = 副本数，W = 写确认数，R = 读取数

```
读写集合有交集的条件：W + R > N（假设同一组 N 个副本）
示例（3 副本）：
  W=3, R=1: 写全部节点，读任意（写代价高）
  W=2, R=2: 读写各过半数（推荐）
  W=1, R=3: 写一个节点，读全部（读代价高）

常见配置：N=3, W=2, R=2（交集成立；是否线性一致仍取决于写入协议、版本排序、并发冲突处理与读修复等机制）
```

`W + R > N` 只说明任意 W 个成功写入副本与任意 R 个读取副本至少相交一个；它本身不保证读到最新值，更不自动推出线性一致。系统还必须定义版本/时间戳比较、并发写冲突、读修复和失败副本处理。若实现采用 sloppy quorum、读取的副本集合变化或并发写入，简单交集推理也不够。

例如 N=3、W=2、R=2 时，写入成功集合与读取集合至少共享一个副本；读路径仍需比较有效版本并按系统协议收敛，不能仅凭“存在交集”就断言读到了最新提交。

---

## 读写模型

### 写入确认与读取策略

多数副本确认只是某些共识/复制协议的一环，不能单独证明写入线性一致。还需要协议规定 leader/epoch、日志顺序、提交条件和读屏障；读取也不能简单地“读所有副本后选最大时间戳”，因为并发冲突和时钟偏差可能令版本顺序不可靠。系统的强读、最终一致读语义应以其协议和 API 文档为准。

### Vector Clock（向量时钟）

```
向量时钟可追踪更新间的因果关系，帮助识别并发冲突；它能指出需要协调的版本，但不替业务自动决定合并规则：

D1 ([A:1])         <- A 写入 v1
D2 ([A:2])         <- A 更新 v2
D3 ([A:2, B:1])    <- B 读取 D2 后更新（有 A 的因果关系）
D4 ([A:3])         <- A 更新 v3（与 D3 冲突！需要合并）
```

## 实现对比

| 系统 | 一致性模型 | 实现方式 |
|------|-----------|---------|
| etcd | 线性一致操作可用 | Raft；读写语义仍要看具体 API/选项 |
| ZooKeeper | 有序更新与会话语义 | ZAB 原子广播协议，不是 Raft |
| Cassandra | 可调一致性级别 | 按请求配置 consistency level；quorum 交集不等于无条件线性一致 |
| DynamoDB | 按操作提供最终一致或强一致读等语义 | 服务托管的复制实现；不要把早期 Dynamo 论文的 vector clock 直接套到 DynamoDB |
| Redis Cluster | 异步复制，故障切换可能丢失已确认写 | 不提供跨分片事务的线性一致保证 |
| MySQL Group Replication | 组内排序与多数派协调；副本应用可异步 | 基于 Paxos 的组通信；一致性读写点受配置影响 |

---

> [!example]- 题型索引
> | 题型 | 要点 |
> |------|------|
> | W+R > N | 在固定副本集合假设下保证读写集合相交；不单独保证最新读或线性一致 |
> | 强一致 vs 最终一致 | 强语义通常增加协调/等待成本；实际延迟与可用性取决于协议、故障和部署 |
> | Vector Clock 用途 | 检测和解决分布式系统中的写冲突 |
> | 读己之写 | 用户总能读到自己的更新（重要用户体验） |
> | 单调读 | 读到新数据后不会读到旧数据（防止"时光倒流"） |
>

> [!tip]- **工程要点**
> 实际系统大多用最终一致性 + 关键路径强一致。如社交平台：发帖（最终一致），点赞数（最终一致），支付（强一致）。Quorum 的 W+R > N 是权衡一致性和性能的关键参数。
