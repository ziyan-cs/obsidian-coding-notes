> [!abstract] 学习定位：从数据真相、业务不变量和故障窗口出发，理解事务、缓存、消息与分布式协调的边界。

> [!summary] 核心摘要
>
> 分布式事务是在原子性、可用性和协调成本之间取舍。2PC 强依赖协调者且可能阻塞，Saga 用补偿换取可用性；无论方案如何都必须处理幂等、重试和人工对账。


这里的核心问题是：一个业务不变量横跨两个**独立提交边界**时，协调者失联、请求超时或重试会让参与方对结果认识不一致。先判断能否把不变量收敛进单一数据库事务，再比较跨服务方案。

# 分布式事务场景

```
订单服务提交订单 → 库存服务预留商品 → 支付服务发起扣款
任何一步都可能在“已生效但响应丢失”时超时。
问题不是简单地再次调用接口，而是先查明业务状态和幂等键，再决定重试、补偿或人工对账。
```

# 方案一：2PC（两阶段提交）

```
协调者（Coordinator / Transaction Manager）

阶段 1（Prepare）：
协调者 -> 参与者 1: Prepare? 参与者 1 -> 持久化可恢复状态并保留必要锁/资源
协调者 -> 参与者 2: CanCommit? 参与者 2 -> 准备资源
参与者全部回复 Yes -> 进入阶段 2
任一回复 No -> 全局中止（回滚）

阶段 2（Commit）：
协调者 -> 参与者 1: DoCommit
协调者 -> 参与者 2: DoCommit
参与者执行 Commit，释放资源，回复 ACK
协调者收到全部 ACK -> 事务完成
```

## 2PC 的问题

| 问题 | 说明 |
|------|------|
| 阻塞 | 参与者阶段 1 后持有资源锁，等待协调者决策 |
| 协调者不可用 | 已准备的参与者可能等待最终决议；协调者恢复需依赖持久决议日志 |
| 部分通知失败 | 某些参与者尚未收到决议，系统须重试并恢复到同一最终结果，不能直接宣布完成 |
| 恢复成本 | 协调者及参与者的日志、超时和重试策略必须经过故障演练 |

3PC 增加阶段和超时规则，但在网络分区和异步网络中，超时不能证明别的参与者已完成同一决议；它不是把 2PC 一键变为“非阻塞且强一致”的工程替代品。

# 方案二：TCC（Try-Confirm-Cancel）

```
业务层面的两阶段（非数据库层面）：

Try：    预留资源（如冻结库存 10 件）
Confirm：确认执行业务（扣减冻结库存）
Cancel： 取消（释放冻结库存）

示例（下单）：
  Try:    库存服务 -> 冻结 1 件商品（状态：已冻结）
  Confirm: 库存服务 -> 扣减冻结库存（状态：已扣减）
  Cancel:  库存服务 -> 释放冻结库存（状态：已释放）
```

| 优点 | 缺点 |
|------|------|
| 不依赖数据库 XA | 业务侵入性强 |
| 不必长时间占用 XA 数据库锁；可用业务预留态 | 预留资源本身仍有并发控制与成本，必须实现 Try/Confirm/Cancel |
| 不要求存储支持 XA | 空回滚、悬挂、重复 Confirm/Cancel、超时恢复需自行处理 |

# 方案三：Saga（长事务）

Saga 将一个大事务拆分为 N 个子事务，每个子事务有对应的补偿操作：

```
正向：T1 -> T2 -> T3 -> T4（正常完成）
失败：T1 -> T2 成功，T3 失败 -> 按业务依赖补偿已完成的 T2、T1

示例（下单 + 扣库存 + 支付）：
  T1: 创建订单
  T2: 扣减库存（C2: 释放库存）
  T3: 扣减余额（C3: 恢复余额）
  T4: 确认订单

  如果 T3 确认未扣款：不执行 C3；释放库存并将订单转为失败。
  如果 T3 结果未知：先按支付流水查询真实状态，不能盲目再次扣款或退款。
```

**Saga 的隔离性：** 子事务提交后对其他事务可见，补偿是新的业务动作而非数据库回滚；外部副作用（如发货、邮件）也不一定能被完全撤销。需要预留态、幂等命令、可恢复的流程状态及人工处理通道。补偿次序由依赖决定，不是机械地“所有步骤严格倒序”。

# 方案四：本地消息表（最终一致）

```
transactional outbox flow
  1. producer commits business state and an outbox row in one local transaction
  2. relay reads unfinished outbox rows and publishes them
  3. relay 可能在发布成功、标记完成之前崩溃；重试会重复发布
  4. consumer 以业务唯一键去重，处理成功后确认；失败可重试/报警
```

**边界：** outbox 解决“本地业务更新成功、消息却没发出”的双写窗口，但不自动消除重复，也不能保证消费者、支付系统等外部副作用恰好一次。需要 outbox 积压监控、唯一键、重试上限与对账。

# 方案对比

| 方案 | 需要的前提 | 主要代价 |
|------|------------|---------|
| 2PC/XA | 所有参与存储支持协调协议与可恢复决议 | 准备阶段占用资源，协调与恢复复杂 |
| TCC | 各参与服务能表达业务预留、确认和取消 | 业务侵入高；悬挂、空回滚、幂等要处理 |
| Saga | 各步能定义补偿或明确不可逆分界点 | 中间态可见；补偿可能失败且不能完全回滚 |
| Outbox | 业务数据与 outbox 可在同一库事务内提交 | relay、去重、积压与最终一致性治理 |

---

选型先问三个问题：哪些数据必须在同一提交边界维护？失败后能否用业务补偿恢复？响应超时后如何查明真实结果？没有一种方案天然“更快”或“更适合支付”；先做最小故障矩阵（提交前/后断网、响应丢失、重复消息、协调者重启）并定义收敛状态。参考 [Microsoft Saga 设计](https://learn.microsoft.com/en-us/azure/architecture/reference-architectures/saga/saga)、[补偿事务](https://learn.microsoft.com/en-us/azure/architecture/patterns/compensating-transaction) 与 [Transactional Outbox 模式](https://microservices.io/patterns/data/transactional-outbox)。
