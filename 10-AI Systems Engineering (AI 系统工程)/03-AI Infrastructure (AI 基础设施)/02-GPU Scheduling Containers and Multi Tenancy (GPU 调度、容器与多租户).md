> [!abstract] 学习定位
> GPU 是昂贵且拓扑敏感的共享资源；调度不仅分配卡数，还要考虑显存、互联、驱动兼容、启动时间和租户隔离。

> [!summary] 核心摘要
>
> 容器封装用户态依赖，但仍依赖宿主驱动与设备插件。调度器需要匹配模型资源、节点能力和数据位置，并用队列与配额保证公平。

# 软件与硬件边界

GPU 容器仍使用宿主机内核与驱动。镜像中的 CUDA 用户态库、宿主驱动和框架版本必须兼容；升级前通过目标节点验证，不能只在开发机运行。

模型加载占用时间和显存。节点扩容完成不代表服务立即可用，还可能等待镜像、权重和 warm-up。

做资源预算时把显存拆成权重、KV cache、临时激活/工作区及运行时开销；batch、上下文和输出长度共同影响 KV 占用。不能因为模型权重“放得下”就认定能服务目标并发。调度前确认宿主驱动与用户态库兼容，调度后用真实推理请求验证 readiness，而不是仅检查容器进程存活。

# 调度约束

- GPU 型号、数量、显存和互联拓扑。
- CPU、内存、网络和本地缓存是否匹配。
- 训练或推理任务能否被抢占、恢复或迁移。
- 租户配额、优先级和等待时间。
- 模型副本、数据与地域要求。

只看 GPU utilization 会漏掉显存瓶颈、CPU 预处理、网络传输和空闲等待。

# 多租户

空间切分（例如支持该能力的设备上的 MIG）、时间共享、MPS 和整卡独占提供不同的隔离与利用率取舍；具体能力与隔离保证取决于硬件、驱动和配置。共享可能带来性能干扰、数据残留和侧信道风险，高敏感工作负载应评估独立节点。

设计多租户压测时，让租户 A 持续提交长上下文任务，同时让租户 B 发送少量交互请求；比较 B 的 P95、超时与拒绝率。再观察 A/B 的指标、缓存与日志是否互相泄漏。性能公平和数据隔离是两种不同验收条件，不能用“GPU 利用率提高”代替。

工作负载身份、网络策略、秘密、镜像来源和设备访问都需最小权限。不能因为任务是“内部 AI”就授予集群管理员。

# 资源发现、拓扑和故障处理

设备插件让调度器看到 GPU 资源，但显存需求、NVLink/PCIe 拓扑、MIG profile、驱动和权重位置通常需要标签、扩展调度器或队列系统表达。多卡任务若跨错误拓扑，通信可能成为主要瓶颈。

在线推理、批处理和训练使用不同优先级与抢占策略。离线任务通过 checkpoint 恢复；在线副本在驱逐前停止接流量并排空。节点故障、GPU reset、ECC 错误和 OOM 要有分类指标与自动隔离，不能只让 Pod 无限重启。

容量实验记录镜像/权重下载、模型加载、warm-up、排队、GPU/显存、CPU 预处理和网络。readiness 只有在模型可真实推理后成功；扩容延迟必须进入容量和降级设计。

参考：[Kubernetes Schedule GPUs](https://kubernetes.io/docs/tasks/manage-gpus/scheduling-gpus/)。

# 容量与成本

记录每模型/租户 GPU 时间、排队、吞吐、失败和单位请求成本。离线任务可使用抢占资源和检查点，在线服务需要预留容量与快速降级。

> [!question]- 理解检查
> Kubernetes 已成功调度 Pod，为什么模型服务仍可能数分钟无法 readiness？

**上线验收**：在目标节点完成镜像与权重下载、模型加载和 warm-up 后，发送真实推理请求才宣布 ready。分别记录冷启动、稳态吞吐、TTFT、逐 token 延迟、显存峰值和 OOM；对共享 GPU 再增加 A/B 租户干扰实验。若扩容时间超过可接受的排队时限，预热容量、准入控制或降级策略必须先到位。
