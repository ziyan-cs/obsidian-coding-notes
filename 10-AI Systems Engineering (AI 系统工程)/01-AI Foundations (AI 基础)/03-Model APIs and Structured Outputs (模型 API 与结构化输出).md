> [!abstract] 学习定位
> 模型 API 是具有配额、延迟、版本和概率失败的远程依赖；结构化输出降低解析歧义，但不能代替语义校验。

> [!summary] 核心摘要
>
> 调用端设置 deadline、并发限制和重试预算；返回 JSON 后仍要验证 schema、范围、权限和业务状态，再允许产生副作用。

# 请求边界

封装模型 provider，业务层依赖自己的接口与错误语义。请求明确模型、输入、最大输出、timeout 和幂等标识。不要让 provider SDK 类型散布到全部业务代码。

流式响应改善首 token 体验，但需要处理客户端断开、半截结构、取消和用量统计。长任务可转异步队列并提供状态查询。

# 错误与重试

区分限流、暂时不可用、请求非法、内容策略拒绝和调用方取消。只对瞬态错误退避重试，并受总 deadline 与费用预算约束。

模型可能已完成推理但响应丢失；若会创建工单、付款或发送消息，副作用必须由业务幂等键保护。

这里需要区分“重试模型推理”和“重试业务动作”。前者可能返回不同建议，后者可能重复执行。对创建工单等操作，服务端以用户意图 ID 建立幂等记录，记录 `pending/succeeded/unknown` 与外部工单 ID；响应丢失时先查询记录和外部状态，不直接再次执行。若外部系统没有幂等接口，则需要对账或人工接管。

# 结构化输出

JSON schema 或受约束解码能提高语法合法率，但合法字段仍可能事实错误、越权或相互矛盾。后端仍需校验类型、长度、租户归属、操作权限、对象状态和审批要求。

# 可观测性与隐私

记录请求 ID、模型、延迟、token、错误分类和费用估算；prompt 与响应可能包含敏感数据，应按数据分类脱敏、采样和控制保留时间。

# 可靠性预算

调用模型前先从上游 deadline 中预留网络、推理、校验和副作用执行时间。若剩余预算不足，应提前拒绝或降级，而不是发出注定超时的请求。重试会放大流量与费用：三层组件各自重试两次，最坏可能把一次用户操作放大为多次下游调用，因此通常只在最靠近失败点的一层重试。

并发限制要与 provider 配额、连接池和业务 SLO 联动。遇到限流时读取服务端提示，使用带 jitter 的退避；积压超过可等待时间时快速失败或进入有界异步队列。客户端取消后应继续传播 cancellation，避免无用户接收的推理仍消耗 token。

# 校验与副作用闸门

结构化输出进入业务前依次经过四层检查：

~~~text
syntax/schema -> semantic constraints -> authorization/state -> execute idempotently
~~~

例如模型返回 `{action: "refund", order_id: 42, amount: 100}`：schema 只能证明字段形状正确；后端还要确认订单属于当前租户、操作者有退款权限、金额未超过可退余额、订单状态允许退款，并以业务幂等键防止重复执行。

工具描述是提供给模型的提示，不是权限边界。真正的权限判断必须发生在工具服务端；高风险动作可要求显式确认、审批或 dry-run。模型生成的资源标识不能直接拼接 SQL、路径或 shell 命令。

# 版本与评估门禁

模型、系统提示、工具 schema、检索策略和安全策略共同组成可发布版本。升级时保存测试集和基线，比较任务成功率、结构合法率、事实引用、拒答、延迟与成本，并对关键失败样本做人工复核。

采用灰度或 shadow traffic 时必须保护用户数据。回滚不仅切换模型名，还要恢复兼容的 prompt、schema 和解析逻辑。生产日志记录版本组合，才能解释同一请求为何在升级前后表现不同。

# 最小故障实验

模拟四类失败：provider 429、响应到一半连接断开、合法 JSON 包含越权对象、工具执行成功但响应丢失。验证 deadline、重试次数、幂等记录、审计日志和用户可见错误是否符合预期。
