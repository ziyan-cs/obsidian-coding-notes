> [!abstract] 学习定位
> 训练改变参数，推理使用固定参数生成结果；生产系统更常面对版本、数据、容量和回滚，而不是从零训练模型。

> [!summary] 核心摘要
>
> 预训练、微调和推理消耗不同资源。后端工程师要记录模型、prompt、数据和评估版本，并让切换、灰度、回滚和兼容性可控。

# 生命周期

~~~text
data -> train or fine-tune -> evaluate -> register
     -> deploy -> observe -> compare -> rollback or promote
~~~

微调适合改变稳定行为模式，不应替代频繁变化的知识；RAG 适合注入可更新证据，但增加检索链路和权限边界。

例如客服机器人需要每日变化的运费规则：优先把权威规则放进可版本化的知识库并检索，保留来源和生效时间；若它长期无法稳定输出约定的分类格式，再考虑用授权数据微调。两种方法可以组合，但微调后的权重不提供“当前规则一定正确”的保证，RAG 也不自动保证引用忠实。

# 推理资源

自回归生成通常包含处理输入的 prefill 和逐 token 生成的 decode。长上下文增加 prefill 成本，长输出增加 decode 时间。批处理提高设备利用率，却可能增加排队和单请求延迟。

量化、并行和缓存会改变成本与质量，结论依赖模型、硬件和负载，必须测量。

# 版本与兼容

一次结果至少能追溯模型标识、服务版本、prompt、检索索引、工具版本和主要参数。供应商更新模型别名时行为可能漂移；关键系统应使用回归集和灰度发布。

切换模型前比较质量、延迟、费用、安全和失败率。同一会话不应无意中来回切换不兼容模型。

# 从数据到发布版本

训练数据、预处理代码、模型权重或供应商版本、tokenizer、prompt/template、推理参数与运行时、许可证和评估集共同构成版本。任何一项变化都可能改变行为，因此发布记录不可只写模型名称。

```text
data snapshot -> train/tune -> offline evaluation -> package
              -> shadow/canary -> online monitoring -> retire
```

训练关注可复现数据与实验、泄漏和偏差；推理关注延迟、吞吐、显存、量化误差和运行时兼容。上线前在目标硬件比较质量、TTFT、吞吐和成本，灰度失败能回到完整的旧版本组合。退役时处理缓存、索引、权重访问和数据保留。

Build/Buy 还要比较数据边界、地区、SLA、配额、可移植性、评估透明度和总成本，不只比较单价。

# Build or Buy

API 上手快且省运维，自部署提供更多控制和数据边界，但需要 GPU、调度、升级与值班能力。选择依据是数据要求、吞吐、延迟、定制、成本和团队能力。

决策表至少列出月请求量、输入/输出长度分布、峰值并发、数据驻留要求、质量门槛和故障时降级方式。API 成本要包含重试和上下文增长；自部署成本要包含闲置 GPU、模型加载、运维和值班。先以相同测试集比较，再决定，不要仅按单次调用报价比较。

> [!question]- 理解检查
> 知识频繁变化时，为什么微调往往不如可更新检索库？哪些场景反而适合微调？

**发布演练**：把一次升级视为“模型 + prompt + 索引 + 工具 schema”的整体发布。先固定 50 条离线回归样本，再用 shadow 比较新旧结果，最后 canary 小流量；分别设置质量、延迟、费用和安全护栏。若用户问题分布、知识库或供应商模型发生漂移，需用版本化的输入、检索结果与工具轨迹定位原因。回放涉及隐私数据时先授权、最小化和脱敏；回滚时恢复兼容的整套版本，而不只改模型别名。
