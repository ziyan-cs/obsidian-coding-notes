> [!abstract] 学习定位
> 用一份能直接填空的设计稿，把需求、边界、失败策略和验收证据固定下来；项目名不是设计理由。

> [!summary] 核心摘要
>
> 项目设计先写用户问题、范围和成功指标，再确定接口、数据模型、关键流程、失败策略与验收证据。技术选型必须对应约束，不能先列技术栈再寻找用途。

复制模板时以文件名作为标题，不再额外写一个 `# 项目名`。以下是**待填写的设计骨架**，不是已经完成的项目成果：

```md

事实来源、关键表、唯一约束：

# 请求路径与失败语义
同步 / 异步路径：
```

# 规则

- “使用 Redis/Kafka”不是设计理由；先说明瓶颈或故障模型。
- 每个异步流程必须定义：谁投递、谁消费、如何重试、如何去重、最终怎样观测。
- 性能结论必须写负载、机器/环境、指标和基线。
- 未实现的设计写“计划”，已测过的写“结果”，不要混淆。

# 从想法到可验收设计

| 顺序 | 必须回答的问题 | 可留下的证据 |
| --- | --- | --- |
| 问题 | 谁在什么场景下受损？ | 用户故事与非目标 |
| 契约 | 输入、输出、错误如何稳定？ | API / event 示例 |
| 数据 | 哪份数据是真相，容量多少？ | schema 与容量假设 |
| 失败 | 超时、重复、乱序如何处理？ | 状态机、重试与幂等策略 |
| 运行 | 如何发现慢、错、满？ | logs、metrics、trace、压测 |

先填前两行再选技术组件。任何“使用某中间件”的决定，都应该能回到一个明确的问题、约束或失败模型；否则它只是名词堆砌。

**填表示例**：短链接的用户故事是“创建一个可过期的短码，访问时跳转到目标网页”；非目标是“第一版不做跨地域和实时分析”。如果预计每天新增 1000 条、平均目标 URL 200 字节，先估算原始 URL 年增量约 73 MB，再把索引、元数据、备份和冗余单独计入；这个量级不支持一开始就引入复杂分布式存储。数字是设计假设，必须在真实项目里重新测量。

# 演示最小闭环

演示时按一条真实请求走：输入校验 → 状态变更 → 失败注入 → 日志/指标定位。一次成功请求只能证明 happy path；再展示一个可预期失败和恢复动作，才算能说明工程边界。
