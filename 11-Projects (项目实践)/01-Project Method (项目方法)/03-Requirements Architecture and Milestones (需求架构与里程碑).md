> [!abstract] 本篇要点
> 项目推进应把模糊目标转成可验收场景、架构边界和短周期里程碑，每个里程碑都留下可运行产物与证据。
>
> 先写用户、场景、输入输出和成功标准，再画系统边界与关键数据流；把项目切成纵向可演示增量，而不是按“先写完数据库、再写完网络层”横向堆模块。每轮只增加一个主要风险，并用测试、日志或压测证明结果。

# 从需求到验收

一个可执行需求至少包含：

- 谁在什么场景下发起操作。
- 输入、输出与错误语义。
- 数据如何变化，哪些不变量必须保持。
- 延迟、容量、安全和可用性约束。
- 可重复的验收步骤。

“做一个高并发服务”不是需求；“在给定硬件与数据规模下，错误率和延迟达到可测目标”才可验证。

# 划定系统边界

```text
client -> API -> domain service -> repository -> database
                     |
                     `-> message/cache/external service
```

对每条跨边界调用写清超时、重试、幂等与失败后的用户可见结果。组件图不能只写产品名，还要解释它承担的职责。

# 纵向里程碑

推荐顺序：

1. 单进程、内存数据的最小闭环。
2. 引入持久化和迁移脚本。
3. 补并发控制、幂等与故障处理。
4. 加指标、结构化日志和压测基线。
5. 容器化并在干净环境部署。

每步都应可运行、可回退、可演示。不要让分支持续数周无法集成。

对每个里程碑写清 `输入条件 → 可运行增量 → 自动验收 → 失败回退`。例如短链接第一阶段只有内存存储：输入一个合法 URL，创建短码并重定向；测试覆盖重复创建、非法 scheme 和不存在短码；若设计改变，删除实验数据即可回退。第二阶段引入数据库时，验收变为“进程重启后映射仍存在”，并增加迁移失败的回退方案。

# 风险驱动决策

优先验证最可能推翻设计的假设，例如热点写入、消息重复、断线重连或外部 API 限流。低风险的页面美化和抽象重构不应抢占早期验证时间。

# 里程碑验收单

- [ ] 一条主路径从请求到数据落盘可以演示。
- [ ] 至少一个失败场景有确定响应和日志。
- [ ] README 中的命令能在干净环境复现。
- [ ] 新增复杂度对应一个已说明的真实约束。
- [ ] 本轮结果有测试、抓包、指标或压测证据。

# 考察题目

## 1. 动手题

把项目拆成三次可运行纵向切片，每次指定接口、数据状态与自动化验收。

> [!note]- 验收要点
> 每一步从请求到结果可演示，风险与依赖按顺序消减，不用“完成某一层”代替交付。

## 2. 机制追问

为什么项目里程碑应以可运行纵向切片划分，而非“先写完数据库层”？

> [!note]- 参考答案
> 纵向切片从入口到结果验证真实契约与集成风险，每步有可演示增量；横向分层完成不代表系统能工作。
