> [!abstract] 学习定位
> 即时通信要分开处理连接生命周期、消息投递与用户已读；每层都有独立的失败与重试语义。

> [!summary] 核心摘要
>
> 心跳只能推断连接可能存活，broker ACK 只能说明投递或消费阶段，已读回执才是用户看到的业务证据；三者不能互相替代。

# 最小范围

- 第一版做单机 WebSocket 连接管理；原始 TCP 自定义帧是独立的后续练习，避免同时维护两套协议。
- 心跳、登录/登出、单聊消息、离线消息占位。
- 不做端到端加密、群聊大规模 fan-out、多机全局顺序。

# 单聊的最小数据契约

```json
{"message_id":"uuid","conversation_id":"c42","sender_id":"u1","sequence":18,"body":"hello"}
```

`message_id` 用于去重；`conversation_id + sequence` 用于定义一个会话内的顺序范围；`sender_id` 用于权限和审计。服务端写入消息后再通知接收方，客户端重连时按最后确认的 sequence 拉取缺口，不能依赖一次 WebSocket 推送必达。

发送请求还应带客户端生成的 `client_message_id`。服务端从已认证连接确定 `sender_id`，在同一事务中检查会话成员资格、去重并持久化消息；成功回执返回服务端 `message_id` 与 `sequence`。客户端重试沿用同一个 `client_message_id`，否则服务端无法识别“同一次发送”。

# 连接状态与单机结构

每条连接由一个读循环负责解析客户端帧，一个写循环串行发送服务端帧；业务 goroutine 不直接并发写 socket，而是把消息放入有界发送队列。这样能明确写所有权，并对慢客户端实施断开、丢弃非关键通知或限制积压。

```text
accept/auth -> session registry
                 |
socket read -> validate -> message service -> durable store
                 |                    |
                 +---- ack <----------+
                                      +-> recipient send queue
```

状态机至少包含 `connecting -> authenticated -> active -> closing -> closed`。每个状态允许的事件不同：未认证连接不能发业务消息；进入 closing 后不再接受新发送；closed 必须从 registry 移除且 writer 退出。

心跳只能表示一段时间内收到了应用层活动。超时阈值要容忍移动网络抖动；过短造成误断，过长增加僵尸连接和资源占用。TCP keepalive 可补充发现半开连接，但不能替代业务心跳和登录状态。

# 消息状态与存储

```text
accepted -> persisted -> delivered -> acknowledged/read
              |
              +-> offline pull after reconnect
```

第一版使用数据库保存消息和会话内单调 sequence。发送请求携带客户端生成的 idempotency key，数据库以发送者与 key 的唯一约束避免重试创建两条消息。服务端成功 ack 表示“已持久化并分配 sequence”，不冒充“对方已读”。

会话序号必须由持久化事务分配或受唯一约束保护，不能由多个 handler 读取当前最大值后各自加一。单机可用会话行锁加序号；它简单但会成为热门会话的串行瓶颈，需先测量再优化。数据库提交成功而 ack 丢失时，客户端重试应返回同一条消息与序号。

客户端保存最后确认 sequence，重连后调用同步接口拉取缺口。实时推送只是降低延迟，持久化日志和按序补拉才是恢复事实。多设备场景要明确已读位置属于用户、设备还是会话；第一版可以只支持单设备并写成非目标。

# 背压、顺序与扩展

单会话内由一个逻辑写入者或数据库序列保证顺序；不同会话之间不承诺全局顺序。发送队列必须有容量：满时阻塞多久、丢哪些消息、是否断开客户端都应是明确策略。presence、typing 等短暂事件可以丢弃，聊天消息不能只存在内存队列。

扩展到多实例时，再引入连接路由和 broker：用户到实例的映射需要租约/心跳；broker 至少一次投递意味着消费者和客户端仍需去重。不要在单机尚未证明状态机和恢复前先堆 Kafka。

# 测试与运行证据

- 状态机单测：重复登录、未认证发送、关闭竞态。
- 协议测试：WebSocket 库已处理底层 TCP 分包；应用层重点覆盖非法 JSON/二进制消息、超大帧、未知类型与不完整业务字段。若另做原始 TCP 协议，再单独测试长度前缀和半包/粘包。
- 并发测试：`go test -race`，连接注册/注销与关闭同时发生。
- 慢客户端：发送队列耗尽时内存保持有界，其他用户不被拖慢。
- 断线恢复：在 ack 前后断开，重连后既不丢消息也不重复副作用。
- shutdown：停止接入、通知连接、等待期限、持久化在途状态。

监控在线连接数、认证失败、收发消息、发送队列深度、投递延迟、离线积压、断开原因和 goroutine 数。压测脚本必须模拟真实连接寿命、心跳和消息速率，不能把反复握手的数字当稳定会话吞吐。
