
> 解决了单线程模型"业务处理阻塞"的问题

# 模型结构

```
┌────────────────────────────────────────────────────┐
│                    主线程                           │
│  ┌──────────┐   ┌──────────┐   ┌────────────────┐  │
│  │  Reactor │──>│ Acceptor │──>│    Handler     │  │
│  │ (epoll)  │   │ (accept) │   │  (read/write)  │  │
│  └──────────┘   └──────────┘   └────────┬───────┘  │
└──────────────────────────────────────── │ ─────────┘
                                          │ 业务逻辑分发
                               ┌──────────▼──────────┐
                               │     线程池           │
                               │  ┌───┐ ┌───┐ ┌───┐  │
                               │  │ T1│ │ T2│ │ T3│  │
                               │  └───┘ └───┘ └───┘  │
                               └──────────┬───────────┘
                                          │ 处理完成，结果写回
                                    Handler.write()
```

# 工作流程

1. 主线程 Reactor 监听事件，Acceptor 接受新连接
2. 读事件到来，Handler 在**主线程**完成 `read()`，将数据和请求投递给线程池
3. 工作线程处理业务逻辑
4. 处理完成后，结果返回主线程（或直接由工作线程）调用 `write()` 发送响应

# 优点

- 业务处理与 I/O 解耦，业务耗时不影响 I/O 响应
- 能利用多核 CPU 处理业务

# 缺点

- **单 Reactor 仍是瓶颈**：所有 I/O 事件（accept + read + write）都在一个线程处理
- 高并发下，单 Reactor 的 epoll_wait 和 I/O 读写本身可能成为瓶颈
- 工作线程写回结果时需要注意线程安全（共享的 fd）
