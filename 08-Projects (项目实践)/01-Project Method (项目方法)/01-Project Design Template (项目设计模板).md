# 30 秒回答

**核心结论**：一句话：为谁解决什么问题；不承诺解决什么。

```md
---
tags: [project/backend]
status: seed
---
# 项目名


## 用户故事与非目标
## API / 事件契约
## 数据模型与容量假设
## 架构与请求路径
## 一致性、失败与重试
## 安全与权限边界
## 可观测性：logs / metrics / traces
## 测试、压测与结果
## 已放弃的方案与理由
## 面试表达：30 秒 / 3 分钟 / 深挖问题
```

# 规则

- “使用 Redis/Kafka”不是设计理由；先说明瓶颈或故障模型。
- 每个异步流程必须定义：谁投递、谁消费、如何重试、如何去重、最终怎样观测。
- 性能结论必须写负载、机器/环境、指标和基线。
- 未实现的设计写“计划”，已测过的写“结果”，不要混淆。

# 从想法到可验收设计

| 顺序 | 必须回答的问题 | 可留下的证据 |
| --- | --- | --- |
| 问题 | 谁在什么场景下受损？ | 用户故事与非目标 |
| 契约 | 输入、输出、错误如何稳定？ | API / event 示例 |
| 数据 | 哪份数据是真相，容量多少？ | schema 与容量假设 |
| 失败 | 超时、重复、乱序如何处理？ | 状态机、重试与幂等策略 |
| 运行 | 如何发现慢、错、满？ | logs、metrics、trace、压测 |

先填前两行再选技术组件。任何“使用某中间件”的决定，都应该能回到一个明确的问题、约束或失败模型；否则它只是名词堆砌。

# 演示最小闭环

演示时按一条真实请求走：输入校验 → 状态变更 → 失败注入 → 日志/指标定位。一次成功请求只能证明 happy path；再展示一个可预期失败和恢复动作，才算能说明工程边界。



# 从零建立模型

本页主题是 **01-Project Design Template (项目设计模板)**。项目笔记要先把“用户问题—接口契约—数据变化—失败处理—证据”连成一条线。功能清单只是起点；如果不能说明失败时系统会做什么、如何观察，就还不是可交付的工程设计。

# 最小实践

选择一条主请求，画出输入、验证、状态变化、下游调用和响应。再人为让一个下游超时，写出重试、用户可见结果和日志/指标应该如何变化。

# 工程检查点

不要以中间件名词代替设计理由。技术选型必须能回到容量、延迟、一致性、安全或运维约束，并能留下一条可复现实验或测试证据。



# 渐进练习

1. **第一步 · 理解**：读：用一条用户请求串起接口、数据变化和下游依赖。
2. **第二步 · 实现**：写：列出一个失败场景（超时、重复或库存不足）与期望对外响应。
3. **第三步 · 验证**：证：保留测试、日志或压测截图对应的命令与结论，形成可复述证据。

# 常见误区

- 先堆功能、后补边界，导致接口、数据一致性和失败处理都无法验证。
- 缺少测试、压测、日志或复现步骤，项目难以作为工程能力证据。

# 学习闭环

## 从零复述

- 不看正文，用“问题 → 机制 → 边界”三句话讲清 **01-Project Design Template (项目设计模板)**。

## 最小验证

- 写一个最小代码、命令、测试或项目观察，亲自验证本页的一条关键结论。

## 自测

1. 它解决的工程问题是什么？
2. 核心机制在哪个环节生效？
3. 什么时候应当换用另一种方案？
