> [!abstract] 完成标准
> 项目用于证明你能把语言、系统、数据和工程工具组合成可运行的软件。完成的项目必须可复现、可演示、可解释，也能诚实说明未解决的问题。

# 问题与边界

- [ ] 能用用户、场景、输入输出、SLO 和非目标描述问题，而不是先罗列技术栈。
- [ ] 能估算请求量、数据量、并发、延迟和资源预算，并说明估算假设。
- [ ] 能画出核心组件、数据流、同步/异步边界和故障传播路径。
- [ ] 能把需求拆成可验证的里程碑，每个阶段都有可运行增量。

# 实现质量

- [ ] 接口、配置、错误、日志、数据模型和并发所有权具有一致约定。
- [ ] 关键路径有单元测试、集成测试与边界测试，测试能阻止真实回归。
- [ ] 服务具备超时、资源上限、幂等或重试边界、健康检查与优雅关闭。
- [ ] 敏感信息不入库，依赖和环境可复现，README 能让陌生人启动项目。

# 运行证据

- [ ] 保存功能演示、测试结果、基准方法、关键指标和故障注入结果。
- [ ] 性能结论包含环境、负载模型、样本和瓶颈分析，而非只给一个 QPS。
- [ ] 至少复盘一次真实缺陷：现象、证据、根因、修复和防回归措施齐全。
- [ ] 能说明容量上限、单点、数据一致性窗口和下一步改进优先级。

# 表达验收

- [ ] 能在 30 秒内说明项目解决什么问题、自己负责什么和结果如何验证。
- [ ] 能在 3 分钟内沿一次请求讲清架构、关键取舍与失败处理。
- [ ] 面对追问能回到代码、日志、测试或数据证据，不夸大个人贡献。
- [ ] 能解释至少两个被放弃的方案以及当时的选择条件。

# 综合自测

1. 如果删除项目中的技术名词，你还能否清楚说明它解决的业务或工程问题？
2. 服务依赖数据库与缓存时，任一依赖超时或部分失败会发生什么？
3. 你的压测是否测到了目标路径，客户端、网络或日志是否反而成为瓶颈？
4. 陌生人在一台干净机器上能否按 README 在 15 分钟内运行核心演示？
