## 实现概述

项目奠基版本，目标是把 TCP Socket 理论落地，同时搭好后续模块化扩展的基础框架。

核心参考《TCP/IP 网络编程》，先梳理框架再独立手敲实现，每一个系统调用都确认过语义再用。 CMake 多模块构建参考示例写成，理解根目录与子模块的分工方式后照着实现。

当前阶段聚焦 server 模块，实现 `main` 入口调用，`echo` 回声功能作为 server 的内置逻辑。

**完整调用链：**
`socket()` → `setsockopt()` → `bind()` → `listen()` → `accept()` → `recv() / send()` → `close()`

## 模块设计

刻意实践模块化与职责分离，便于后续维护、扩展。

- `Config` 类 —— 服务器配置管理
	集中管理端口、IP、backlog、缓冲区大小等参数，支持默认初始化与自定义覆盖，避免魔法数字散落各处的问题。
	
- `Server` 类 —— Socket 生命周期封装
	采用分层设计，职责边界清晰：
	- 底层接口 `creatSocket`、`setSocketOpt`、`bindSocket`、`listenSocket`
	- 整合接口 `init`、`run`、`stop`
	- 内置统一日志接口 `log()`，便于后续替换为异步日志系统
	
- `main.cpp` —— 入口与业务解耦
	仅调用初始化和启动接口，不掺杂业务代码，保证程序结构清晰。

## 遇到的问题

### Telnet 逐字符发送，`recv()` 每次只收到 1 个字节

**现象：** 客户端输入字符串触发服务器端 `recv()` 多次读取，每次仅接收 1 字节。

**排查**：初步判定为 `recv()` 逻辑错误，后续反复排查无果，重新查看 TCP 协议性质。

**核心认知：** 
- Telnet 默认以逐字符模式运行，每次按键触发一个 TCP 段
- 本质是 **TCP 字节流** 无消息边界，内核负责自动传输字节流，发送与接收次数无对应关系

**结论：** 这是正确行为，不是 bug。

消息边界的界定责任在应用层协议（后续 HTTP 解析阶段将正式处理此问题）

## 遗留与展望

**根本瓶颈：单线程阻塞 I/O**

`accept()` 与 `recv()` 均为阻塞调用，主线程串行处理——同一时刻只能服务一个客户端， 第二个连接进来只能等第一个断开。

**为什么不考虑 thread-per-client 过渡**

多线程阻塞符合直觉：来一个连接开一个线程
但线程创建与销毁的开销随并发量线性增长，连接一多就变成了资源消耗问题而非并发问题。 这条路走不远，跳过它直接演进到事件驱动模型更有意义。

### v0.2 目标：

引入 `epoll` ，实现 I/O 多路复用，从 阻塞单线程”升级为事件驱动并发模型
