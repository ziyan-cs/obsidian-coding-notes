## 实现概述

这是项目奠基版本，目标是用 C++ 将 TCP Socket 理论落地，同时搭好后续模块化扩展的框架。

1. 参考《TCP/IP 网络编程》和相关资料理解每个系统调用的作用，
	按照整理的知识笔记手动实现主逻辑。
2. 参考成熟工程示例的 CMakeLists.txt 的写法，按照多模块为可扩战框架
3. 了解后端服务器的通用设计范式，为后续优化（如并发模型、日志模块）预留了扩展空间。

- `main` 作为服务器逻辑入口，与业务代码解耦
- 聚焦 server 模块，`echo` 回声功能作为内置逻辑

**完整调用链：**
`socket()` → `setsockopt()` → `bind()` → `listen()` → `accept()` → `recv() / send()` → `close()`

## server 模块设计

刻意模块化与职责分离设计，便于后续维护、扩展。

- `Config` 类：
	- 集中管理端口、IP、backlog、缓冲区大小等参数，支持默认初始化与自定义覆盖，避免魔法数字散落各处的问题。
	
- `Server` 类：
	- 封装 Socket 完整生命周期，分层设计
	- 底层接口 `creatSocket`、`setSocketOpt`、`bindSocket`、`listenSocket`
	- 整合接口 `init`、`run`、`stop`
	
- `main.cpp`
	- 仅调用初始化和启动接口，不含业务代码，保证主程序结构清晰。

## 遇到的问题

### Telnet 逐字符发送，`recv()` 每次只收到 1 个字节

**现象：** 客户端输入字符串，服务器端每次仅接收 1 字节。

**排查**：起初判定为 `recv()` 逻辑错误，后续排查无果，重新查看 TCP 协议性质。

**核心认知：** 
- Telnet 默认以逐字符模式运行，每次按键触发一个 TCP 段
- 本质是 **TCP 字节流** 无消息边界，内核负责自动传输字节流，发送与接收次数无对应关系

**结论：** 是正确行为，不是 bug。

>消息边界的界定责任在应用层协议（后续 HTTP 解析阶段将正式处理此问题）

## 遗留与展望

**瓶颈：单线程阻塞 I/O**

`accept()` 与 `recv()` 均为阻塞调用，同一时刻只能服务一个客户端， 第二个连接进来只能等第一个断开。

**为什么不考虑 thread-per-client 过渡**

多线程阻塞符合直觉：来一个新连接就开一个线程

但线程创建与销毁的开销随着并发量线性增长，连接一多就会变成资源消耗问题。

跳过此实现直接演进到 I/O 多路复用更有意义。

**v0.2 目标：**

引入 `epoll` ，实现 I/O 多路复用，从 阻塞单线程”升级为事件驱动并发模型
