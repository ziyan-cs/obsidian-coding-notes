> [!abstract] 学习定位
> SLO 把“足够可靠”写成用户可感知的目标，错误预算用于平衡可靠性与发布速度，告警只应在需要行动时打断人。

> [!summary] 核心摘要
>
> 先定义代表用户体验的 SLI，再设置时间窗口和目标。消耗错误预算过快时限制高风险变更并优先修复可靠性，而不是追求没有成本边界的 100%。

# 从用户体验定义 SLI

常见 SLI 包括成功请求比例、满足延迟阈值的请求比例、数据新鲜度和任务按时完成率。分母、排除项和测量位置必须清楚，否则同一指标会得到不同结论。

~~~text
availability SLI = good requests / valid requests
error budget = 1 - SLO target
~~~

健康检查成功不代表用户请求成功；客户端、边缘和服务端测量各有盲区。

# 错误预算

SLO 不是每分钟都必须达标，而是在滚动窗口中允许有限失败。预算燃烧率比单一瞬时阈值更能同时发现快速事故和慢性退化。

预算充足时可承担合理变更；持续超支时应减少风险、修复依赖与容量问题。错误预算不是“允许主动制造故障”的配额。

# 告警设计

告警需要明确影响、紧急程度、负责人和运行手册。分页告警对应用户影响或即将耗尽的预算；只需要观察的趋势进入仪表盘或工单。

避免按单机 CPU 短暂升高直接分页。先看服务级成功率和尾延迟，再用资源指标定位原因。

# 写出可计算的 SLI

以“30 天内 99.9% 合法请求在 300 ms 内成功”为例，需要定义：哪些状态算成功、超时由谁观测、客户端取消是否进入分母、后台任务如何计量，以及维护窗口是否排除。模糊的“服务可用率”无法驱动决策。

```text
good events  = valid requests with expected result and latency <= 300 ms
valid events = all eligible requests observed at chosen boundary
SLI          = good events / valid events
```

不同用户旅程可以有不同 SLI：读请求、写请求、异步任务新鲜度和数据正确性不应混成一个数字。服务端指标可能看不到边缘、DNS 和客户端故障，关键路径需要选择最接近用户的测量点或补充外部探测。

# 错误预算与燃烧率

99.9% 目标意味着窗口内允许 0.1% bad events。燃烧率表示当前消耗速度相对预算允许速度的倍数：短窗口高燃烧捕获快速事故，长窗口较低燃烧捕获慢性退化。实际阈值按团队响应能力和 SLO 窗口设计，不照抄固定数字。

错误预算策略应事先说明：预算健康时允许哪些风险；接近耗尽时减少什么变更；已经耗尽时由谁批准例外。预算不是处罚研发，而是把发布速度和可靠性放进同一决策框架。

# 告警验证

每条分页告警都要能映射到用户影响、值班动作和 runbook。使用历史事故或合成故障回放，检查是否及时触发、恢复时是否自动清除、低流量时分母是否造成噪声。

月度评审检查 SLI 定义、缺失数据、排除条件、告警负担和预算决策是否仍有效。业务目标变化时更新 SLO，而不是通过修改查询隐藏违约。

实践：为一个 Go API 从原始 histogram/counter 写出 SLI 查询，注入 5xx 与延迟，记录多窗口告警的触发和恢复过程。

# 评审

定期检查 SLI 是否仍代表产品体验，排除项是否掩盖故障，告警是否可行动。每次事故都应验证现有信号为何及时或未能发现问题。
