> [!abstract] 学习定位
> 容量规划同时约束性能、可靠性和成本；自动扩缩只能响应可观测信号，不能修复无界队列、热点或错误资源模型。

> [!summary] 核心摘要
>
> 从单位工作资源成本、流量增长和故障冗余估算容量，再用负载测试验证。扩缩指标要领先于用户故障，并考虑启动时间、冷却和下游上限。

# 容量模型

先确定单位请求或任务消耗的 CPU、内存、连接、磁盘与下游配额，再考虑峰值、增长和单区故障。平均利用率不能描述热点和尾延迟。

容量至少包含正常峰值、发布额外实例、节点维护和故障冗余。数据库连接、消息分区和外部 API 配额往往比 Pod 数更早成为瓶颈。

# 从吞吐推导并发与资源

Little's Law 给出稳态直觉：`并发在途量 ≈ 到达率 × 平均停留时间`。若 500 req/s、平均 80 ms，则平均约 40 个请求在途；尾延迟、突发和重试会让峰值更高。这个估算帮助设置连接池、队列和实例数，但必须用真实分布验证。

把资源模型写成可测假设：每请求 CPU 时间、分配量、数据库连接占用、下游 QPS 和响应大小。随后乘以目标流量、峰值系数、增长和故障冗余，并为发布时双版本共存留余量。

# 扩缩信号与闭环

HPA 使用 CPU 时，request/limit 设置会影响利用率含义；等待数据库的服务 CPU 可能很低，却已完全饱和。异步 worker 更适合使用队列年龄、积压与单任务处理时间；在线服务可结合并发、请求率、尾延迟和连接池等待。

```text
observe -> decide desired replicas -> start instances -> become ready
        -> receive load -> metric changes -> stabilize
```

这个闭环存在采集、决策、调度、拉镜像、启动和预热延迟。扩容前需要过载保护，缩容前需要连接/任务排空。最大副本数还受数据库连接、消息分区、IP 和外部配额限制。

# 容量实验

逐步增加开放到达率，找到首次违反 SLO 的资源，并确认压测器不是瓶颈。分别测试单实例极限、水平扩展效率、单区/节点故障和冷启动。输出吞吐—延迟—资源曲线，而不是一个最大 QPS。

成本按成功请求或有效任务归一化，同时观察 headroom。盲目提高利用率会减少故障余量；购买更便宜实例若增加尾延迟和重试，也可能提高总成本。

官方参考：[Kubernetes Horizontal Pod Autoscaling](https://kubernetes.io/docs/tasks/run-application/horizontal-pod-autoscale/)。

# 自动扩缩

CPU 适合计算型负载；队列长度或等待时间更适合异步 worker；并发数和请求率可用于 I/O 服务。指标必须能反映尚未造成用户失败的压力。

扩容有启动延迟，缩容会影响缓存与在途任务。设置最小/最大规模、稳定窗口和排空策略，避免指标抖动导致反复伸缩。

# 过载保护

当容量不足时，系统应限制入口、应用背压、拒绝低优先级工作并设置重试预算。无界排队只会把即时拒绝变成长时间超时和内存耗尽。

# 成本证据

成本按请求、租户、任务或模型调用归因，结合成功率和 SLO 判断是否值得。Spot/抢占资源适合可恢复任务，不适合没有检查点的关键状态。

优化顺序通常是消除空闲和错误配置、提升利用率、改算法与缓存，最后才用更复杂的平台机制。
