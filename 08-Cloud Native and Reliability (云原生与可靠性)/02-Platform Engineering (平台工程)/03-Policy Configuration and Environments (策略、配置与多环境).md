> [!abstract] 学习定位
> 配置决定同一产物在不同环境中的行为；策略限制哪些配置允许进入生产，两者都必须可验证和可审计。

> [!summary] 核心摘要
>
> 构建产物保持一致，环境差异通过有 schema 的配置与秘密注入表达；策略在提交、部署和运行阶段阻止危险组合。

# 配置模型

配置应有类型、默认值、必填项、范围和废弃周期。服务启动时一次性校验并在错误时快速失败；不要等第一条请求才发现配置缺失。

环境变量适合简单值，但复杂层级需要配置文件或配置服务。秘密与普通配置分开管理，日志只记录来源、版本和非敏感摘要。

# 多环境交付

开发、测试和生产应尽量使用相同产物与部署机制，差异只保留规模、端点、权限和明确功能开关。复制整套配置会让修复无法同步。

功能开关需要负责人、过期时间和监控。长期保留的开关会形成难以测试的组合状态。

# Policy as Code

策略可检查镜像来源、资源限制、特权模式、公开端口、标签和地域要求。策略分层执行：

- 提交阶段快速反馈格式与静态规则。
- 部署阶段拒绝违反安全与治理要求的资源。
- 运行阶段发现漂移与异常行为。

策略应包含清晰错误信息、测试和例外流程。无法解释的拒绝会促使团队绕过控制。

# 配置契约和环境晋升

每项配置记录类型、单位、范围、默认值、是否敏感、动态/静态生效方式和废弃版本。启动时输出非敏感配置摘要与来源，便于判断实例实际加载了什么；动态配置则需要版本、校验、原子切换和 last-known-good。

```text
same artifact digest
 dev config -> test config -> production canary -> production
```

环境晋升的是已测试制品和声明，不是在每个环境重新构建。配置变化与代码变化一样经过 diff、评审、灰度和回滚；数据库端点、权限和资源规模等差异要显式，不通过复制整目录长期分叉。

# 策略执行层次

策略可以在 schema 校验、CI、Kubernetes admission 和运行时审计多个阶段执行。越早反馈越便宜，越靠近运行环境越能看到真实对象；关键规则通常需要两者组合。

拒绝规则应返回对象、字段、违反原因和修复建议。例外包含申请人、业务原因、补偿控制和到期时间，并进入审计；没有到期的例外会逐渐变成永久漏洞。

策略测试至少包含允许、拒绝和例外样本。策略升级先以 audit 模式观察现有对象，再逐步 enforce，避免一次更新阻断所有部署。对策略引擎不可用时是 fail-open 还是 fail-closed，需要按风险和可用性明确决定。

# Feature flag 与秘密

功能开关应有 owner、创建/到期时间、目标规则、默认值和监控。发布完成后及时清理旧分支；权限控制开关不能只在前端判断。

秘密系统保存值，部署配置只保存引用。工作负载通过短期身份获取秘密，轮换时允许新旧凭据短暂重叠并验证消费者已切换。任何渲染、plan、错误日志和调试 bundle 都要检查是否泄密。

官方参考：[Kubernetes Validating Admission Policy](https://kubernetes.io/docs/reference/access-authn-authz/validating-admission-policy/)。

# 变更安全

配置变更也需要评审、灰度、回滚和审计。兼容性涉及旧实例、新实例和共享数据；“只改 YAML”并不代表风险低。
