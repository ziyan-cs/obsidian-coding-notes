> [!abstract] 学习定位
> 内部开发者平台通过自助能力和黄金路径降低交付认知负担，但不能变成隐藏复杂度、阻塞团队的新工单系统。

> [!summary] 核心摘要
>
> 平台把构建、部署、观测、安全和资源申请封装为有边界的产品；黄金路径提供推荐默认值，同时保留受控逃生口和清晰责任。

# 平台解决的问题

团队规模扩大后，每个服务重复配置 CI、镜像、监控、权限和发布策略会造成漂移。平台通过模板、API、CLI 或门户提供一致能力，目标是缩短安全交付时间，不是追求工具数量。

平台团队要像产品团队一样识别用户、成功指标和反馈。只建设门户而没有可靠底层能力，会得到漂亮但无用的界面。

# 黄金路径

一条服务黄金路径通常包含：

1. 从模板创建仓库与所有权信息。
2. 统一构建、测试、SBOM 和镜像发布。
3. 声明资源、身份、网络和配置。
4. 自动部署、健康检查、渐进发布和回滚。
5. 默认接入日志、指标、trace、SLO 与值班信息。

默认值应安全且可运行。特殊工作负载可以偏离，但要声明原因、负责人和运维责任。

# 边界与反模式

- 平台不替业务团队承担服务正确性和线上责任。
- 不要求所有语言共享同一运行时细节，只统一可观察契约。
- 避免把每个操作变成人工审批；高风险权限才需要额外控制。
- 平台 API 和模板需要版本兼容与迁移路径。
- 衡量 lead time、部署成功率、恢复时间和开发者反馈，而不是创建了多少组件。

# 把平台能力写成产品契约

平台不是一组共享脚本，而是一组有版本、有 SLO、有支持边界的能力。服务团队需要知道输入、输出、默认值、失败时由谁处理，以及如何离开黄金路径。

```text
service specification
 -> repository and CI template
 -> build artifact / SBOM
 -> runtime identity and configuration
 -> deployment / rollout
 -> logs, metrics, traces and ownership catalog
```

控制面负责接收服务声明、生成或协调资源；业务数据面仍由各服务运行。平台控制面故障不应让所有业务请求同步失败，因此要区分“无法创建新变更”和“现有服务不可用”。

# 黄金路径的设计原则

- 默认安全：非 root、最小权限、资源限制、网络与秘密边界。
- 默认可观测：统一 service/version/environment 字段和健康契约。
- 可组合：服务按需选择数据库、队列等能力，不生成无法维护的大模板。
- 可升级：模板更新后已有服务能收到迁移提示或自动变更，而不是永久复制旧代码。
- 有逃生口：偏离者声明原因、风险和责任，平台保留最低合规门槛。

平台模板本身要有测试：生成项目后执行构建、单测、镜像扫描、部署和 smoke test。只验证模板渲染成功，不能证明产物真的能运行。

# 采用率与效果

衡量首次成功部署时间、变更 lead time、失败部署率、恢复时间、支持工单和开发者满意度。采用率低时先访谈摩擦点；强制接入可能掩盖平台不可靠、文档不足或抽象不适合。

最小实践应让第二个团队不修改平台内部代码即可创建 Go 服务，完成构建、部署、观测和回滚；随后故意制造失败，验证错误信息能指向用户可执行的下一步。

官方参考：[CNCF Platform Engineering Technical Community Group](https://tag-app-delivery.cncf.io/whitepapers/platforms/)。

# 最小实践

为 Go 服务定义一个模板：健康检查、Dockerfile、CI、Kubernetes workload、资源限制、结构化日志和回滚说明。再用第二个服务验证模板是否真正可复用。
